# 规格写作规范（全仓）

各设计的 LRS（`designs/<根>/lrs.<顶层>.md`）与 LLD（`lld.<顶层>.md`）都按这份写（用户 2026-10-04 评审第一份 LRS 时定，内部#119、内部#126；
LLD 部分与句子层面的规则 2026-10-05 定，内部#203）。**总原则：可读性优先，多用架构图、流程图，少用长篇文字。**
本文是**写 LRS 的人读的规范**：其中的通用规则在全仓默认成立，LRS **不写也不引用**本文；只对某个设计成立的
内容，由那个设计把内容直接写进 LRS（见第 1 节「引用」）。模板在 `flow/templates/design-root/`，
机械检查的条款在 `openspec/specs/repo-layout/spec.md`「专用设计的 LRS 与 LLD 必须有必填节与需求追溯」。

## 1. LRS 写给谁、写什么

- **黑盒**：只写外部看得到的行为与约束，按功能写，不按模块分。流水、内部结构、子模块划分写 LLD。
- **只写最终规格**：LRS 是给读者的定稿，不是工作记录。下面这些**不写在 LRS**，写进设计根的跟踪文档
  `doc/track.<顶层>.md`（模板 `flow/templates/design-root/doc/track.md`）：
  - 结论进展标记：【定】【暂定】【待定】【过渡】；
  - 确认记录：「用户某日确认」「某会话提出」；
  - 开发进展：哪些已实现、哪些还没有；集成期间的过渡端口；
  - 文档的地位说明、来历、标记说明、编号段表。
- **第 1 章之前只留修订记录**（第 0 节可以叫「文档信息」或「修订记录」）。
- **引用只来自 LRS 内部**：除 `doc/` 下的图之外，LRS 里的引用只指向 LRS 自身的节、R 号、表。不引用本文、
  设计根里的存档或旧 spec、LLD、提交号——那些文档会改、会删；需要的内容直接写进 LRS（内部#126）。
- **已删除的需求不留在 LRS**：整条删掉，编号与原因记在跟踪文档「已删除的需求编号」一节；LLD 追溯表跟着删。
  编号只增不复用。
- **新功能不影响旁路**（全仓默认成立，LRS 不写；用户 2026-10-13 定，内部#286）：新功能的开关关掉时，旁路通路的行为与时序都不受影响。

## 2. 通用约定

全仓默认如下，LRS 不写；某个设计不同时，在它的 LRS「术语」一节写明它自己的约定（直接写内容，不写「例外于全仓规范」）。

- **位序**：bit 0 是 LSB；向量写成降序 `[N-1:0]`。
- **字节序**：小端，总线上第 k 个字节占 `[8k+7:8k]`。
- **地址**：字节地址；「对齐」指按字节数对齐。
- **计数与编号**：从 0 开始。
- **尺寸**：位宽写 bit，容量写 B（字节）；参数名 `_W` 是位宽、`_NUM` 是个数。

## 3. 接口通用规则

valid / ready 握手的接口一律满足下面几条，这是全仓所有 RTL 设计的公共原则（用户 2026-10-12 定，内部#284），LRS 不写，只引用本节：

- **valid 不依赖 ready**：输出的 valid 不能由同一接口的 ready 组合产生。对外接口一律如此；内部汇聚口的例外条件见下面「汇聚口的屏蔽」。
- **握手前不变**：valid 拉高后，直到握手（valid 与 ready 同拍为 1）完成，valid 与全部 payload（含 flg、user、id 等随路字段）保持不变，不撤回。
- **握手后下一拍才可改**：握手那一拍才算这笔传完；valid 与 payload 从握手后的下一拍起才可以变（换下一笔或拉低 valid）。
- **valid 为 0 时 payload 不受约束**：valid 为 0 的拍，payload 可以每拍任意变；valid 为 1 时按上面两条，未握手就保持（用户 2026-10-12，内部#285）。
- **只在握手时推进**：计数器、指针、状态只在握手那一拍推进；经汇聚口进来的请求，它改变的状态（如表项分配）只在仲裁胜出那一拍改变（用户 2026-10-13，内部#286）。
- **功能不依赖打拍配置**：模块之间一律用 valid / ready 握手；TPI 取哪种模式、FIFO 是否直通、深度多少，只影响时序，不影响功能（内部#286）。
- **无握手的接口**（配置、状态、中断、DFX）：写明是电平还是脉冲、何时有效、复位值与生效时机。

**汇聚口的屏蔽（msk）**：这是对「握手前不变」在汇聚口上的细化，不是例外（用户 2026-10-12 定，措辞取评审方 内部#285 issuecomment-6126560587 §3）。
- 多路 valid / req 汇聚到一个选择点（仲裁、轮询、固定优先）时，选择点可以按**参与条件**用屏蔽 `msk` 盖住某一路：被盖住的那一路不参与选择，不算撤回。参与条件只能由选择点自己可见的状态（资源、顺序、互斥、该路已给出的载荷）算出。把选择点连同屏蔽看作一个整体：**已选中的那一路保持到握手**——选中与握手不同拍时，选中之后它的 `msk` 不得变为 1、源端的 valid / req 与载荷不得变；选中即握手（授权受下游 ready 门控）时自然满足。源端在**被盖住期间**放弃请求要在规格里写明理由（为什么不丢事务），否则默认源端 valid / req 一经拉起保持到握手。
- **内部汇聚口的 valid 可以依赖 ready**（用户 2026-10-13 定，内部#286）：同时满足下面三条时允许，对外接口不允许：
  ① 只在设计内部的汇聚口；② 选中即握手：valid 由授权给出，授权受下游 ready 门控；③ 下游 ready 由寄存器给出（如 BWD / BOTH 的 TPI），不成组合环。同一接口的 ready 仍不得依赖 valid。
- 规格里每个汇聚口写清：参与条件（msk 的来源）、选中与握手是否同拍、被盖住期间源端能否放弃。
- 验证口径：`req & ~msk & ~grant |=> (req & ~msk) | msk`（未选中的请求下一拍要么仍在参与，要么被盖住）；选中与握手不同拍的口再加 `selected & ~hs |=> selected & ~msk & $stable(pld)`。

**对端也按这几条**：规格默认上游、下游器件同样遵守，不写成接口前提。另有一条对端默认前提（用户 2026-10-13 定，内部#286，由一个设计的上游前提推广）：
- **对端不组合依赖本方 ready**：对端的 valid 与载荷不组合依赖本方任何 ready，同一接口与别的通道都算。否则接口上可能成组合环（如写数据直通时，上游写数据 → 下游写数据 → 下游 ready → 上游 ready → 上游写数据）。

例外收紧到两种：
- 对端（上游 / 下游器件）不满足某一条：只有用户或真实器件文档明确给出时才能写，条文里标「例外」并注明出处（issue 号或文档名），
  如「下游控制器握手前会改 flg（例外，出处：#nnn）」。规格方不能凭推测写入。
- 本设计自己的输出口：不允许例外。

LRS / LLD 里「握手前可以改 / 撤回」一类、没标「例外」和出处的句子，fast_check 判失败（内部#284 起提示，内部#286 起致命）。

### 3.1 活性：通用前提与通用要求（内部#124）

这里的编号（P、C）只供讨论与验证计划引用，编号只增不复用（P4 已删）。LRS 与 LLD 都不写、不引用这些编号（内部#203）：
P1–P3、C1、C2 默认成立，不写；P5–P7 只对下游是 DRAM 控制器的设计成立，那样的设计把内容直接写进 LRS 的前提里（内部#126）。

**对上游的通用前提**

- **P1**：对已被接收的写命令，写数据最终一定送达，不依赖任何读的返回。
- **P2**：最终一定接收读数据与写响应，且不依赖先接收新的命令或写数据。

**对后级的通用前提**

- **P3**：对已接收的读一定返回数据，对已接收的写一定收下写数据。

**对接 DRAM 控制器的设计另加的前提**（只对下游是 DRAM 控制器的设计成立，那样的设计把内容写进 LRS）

- **P5**：交织 hash 一一对应、对全部流量一致：不同的地址落到不同的 DRAM 位置；读与写、DATA 与 META 用同一套 hash。
- **P6**：hash 不用 col：同一行号、不同 col 的地址落在同一个 DRAM 行、同一个 bank。
- **P7**：按 strobe 写，strobe 为 0 的字节不改 DRAM 内容（颗粒支持数据掩码时直接掩码写；不支持时由控制器内部做 RMW）。

**接口的通用要求**（设计自身必须满足）

- **C1 写数据不等写命令**：一条写命令第一次拉起 valid 后，它的写数据即可送出。
- **C2 各通路最终完成**：在规格的前提下，任何参数与配置组合下，每条被接收的读最终送完并带 `last`；每条被接收的写
  最终收完全部写数据，并恰好收到一条写响应；流量停止后，空闲输出最终为 1。

### 3.2 接口组合依赖表（内部#266）

在 `params.yaml` 里声明了 `iodeps_configs` 的顶层，LRS 要有一张「接口组合依赖」表，写每个输出端口允许组合依赖哪些输入端口。
发布前的 `make iodeps` 按这张表比对实测（白名单）：实测有、表里没允许的一项判 FAIL。所以这张表按下面的固定写法写，工具才读得懂。

- **认表**：表头前两格依次是「输出」「允许组合依赖的输入」，第三格起随意（如「性质」），不解析。一份 LRS 只有一张这样的表。
- **「输出」格**：反引号写的端口名或通配（`` `s_rdat_*` ``），多个用「、」分隔。
- **「允许组合依赖的输入」格**：
  - 只能是反引号写的端口名 / 通配（用「、」分隔），或者「无」；
  - 按参数取值才成立的，用「；」分段，每段前写条件 `` `参数` 取 1 / 2 时：``；条件不满足的段不计；
  - 全角括号里的说明不解析，可以写理由；括号外不能有别的文字（「另加」「与 … 的同名字段」这类说法会判写法错误）。
- **同名绑定**：同一行里输出与输入都含一个 `*` 时，两边的 `*` 指同一串：`` `m_wdat_*` `` ← `` `s_wdat_*` `` 表示 `m_wdat_X` 只依赖 `s_wdat_X`。
- **表外的输出**不组合依赖任何输入端口；时钟、复位与 `sta.static_ports` 里的静态 / 半静态配置输入不计。
- 表里允许、实测没有的项只提示，不判 FAIL。

| 输出 | 允许组合依赖的输入 | 性质 |
|---|---|---|
| `s_cmd_rdy` | 无 | — |
| `m_wdat_*` | `s_wdat_*` | 写数据直通（同名） |
| `m_rdat_rdy` | `M_RDAT_MODE` 取 1 时：`s_rdat_rdy`；`M_RDAT_MODE` 取 2 / 3 时：无 | — |

**允许的接口组合环（可选，内部#281）**：`make iodeps` 还会在同一份依赖上接上外部模型找组合环。外部模型默认按 AXI：对端的 rdy 可以组合依赖我们给它的 vld 与数据。
对端默认遵守握手规则（内部#284：vld 与全部载荷保持到握手，下一拍才可变），不会随我们的 rdy 组合变化。只有用户或真实器件文档明确给出的例外，才在 `params.yaml` 的 `iodeps_loops.rdy_dependent` 里列出。
按对方整体（S 侧 / M 侧）找到的环判 FAIL。确实要允许的，在 LRS 里加一张表：

- **认表**：表头第一格是「环上端口」，后面的格随意（如「理由」），不解析。
- **「环上端口」格**：反引号写的端口名或通配，用「、」分隔，格里不能有别的文字。
- **对上才算**：环上每个端口都要匹配某个通配，每个通配也要匹配到环上的端口；多一个、少一个端口都不算。
- 没有这张表等于不允许任何环。

| 环上端口 | 理由 |
|---|---|
| `m_rsp_rdy`、`m_rsp_*_flg` | 写法示例：下游器件保证同一拍内 flg 不随 rdy 变（举例） |

## 4. LRS 的结构

| 节 | 写什么 |
|---|---|
| 0 修订记录 | 一张版本表，按版本号升序，每行只写版本、日期、改了什么；不写状态标记（【定】【暂定】等）、决策来历（「用户某日定」）、issue 号、答复件路径——这些按版本记进跟踪文档（内部#139） |
| 1 概述 | 应用背景、主要功能、框图（draw.io，见第 6 节）、后面各章怎么分 |
| 2 配置与应用场景 | 每个场景一个小节，配图示，写用途、对应的配置、外部可见的差别；最后一个小节是**共用前提**，按五类写对外前提：对前级的需求、对后级的需求、对配置值的需求、对软件的需求、对参数组合的需求 |
| 3 术语 | 只写术语；本设计自己的约定（与第 2 节不同的）写在这里。第 6–8 章当术语用的词（含图里的标签）都要进术语表（内部#137） |
| 4 参数 | 一张参数表，与参数有关的信息（取值、默认、含义、约束、与其他参数的关系）全在这张表里 |
| 5 接口 | 一个接口一张表：端口行之下紧跟它的字段行（字段行「方向」一格留空）；只解释某个信号（或字段）取值与含义的 R 点写进该行的「含义」格，格首加粗编号（`**R.102** …`）；讲多个接口之间关系或行为性的 R 点列在表下 |
| 6 功能描述 | 外部可见的处理流程与结果，每个功能一个「<功能>规格」小节（见第 5 节） |
| 7 异常与 DFX | 错误检测与上报、注错、可观测性 |
| 8 性能需求 | 频率、吞吐、延迟、面积 / 功耗 |

- 9 个 `##` 节都必填，不适用写一句「不适用」与原因；`###` 小节不适用就删。
- 接口表不成列写「同上一行」：几行共同的生效时机、置位条件在表上方写一句，表里只留各行不同的部分（内部#137）。
- 字段行的写法：「信号」写字段名（如 `.addr` 或 `[47:0] addr`），「方向」留空，「位宽」写字段宽度。
  fast_check 的端口比对跳过方向为空的行。

## 5. 条文写法

- **规格小节的结构**（第 6、7、8 章与第 2 章的场景小节）：

  ```markdown
  ### 6.1 <功能>规格

  #### 规格描述

  - **R.301** <一句简洁、可检验的行为>
  - **R.302** <…>（R 点引用的表、公式放在这里）

  #### 解释说明

  - R.301：<必要的说明；能用图说明的配 draw.io 图>
  ```

  「规格描述」只列 R 点；「解释说明」按 R 编号逐条说明，不需要时整节省略。
- **接口的 R 点进表**：只解释信号取值与含义的需求写在接口表该行的「含义」格里（见第 4 节）。
- **配图判据**（内部#137）：下面三类不只用文字与表，要配图——按拍的行为（首拍 / 末拍、strobe、跨拍的码字）画时序图；
  按序列的行为（回写、命令序列）画序列图；延时分解（性能章）画分段图。
- 编号只增不复用；删掉的需求整条移出 LRS，记在跟踪文档（见第 1 节）。
- **句子层面的写法**（S1–S9，内部#203，用户 2026-10-05 定参照 ASD-STE100 Part 1 改写；S9 由 内部#253 加）：LRS 的 R 条文与 LLD 的条目都按这 9 条写。
  「检查」一列写「致命」「提示」的由 fast_check 查（见下）；其余由评审看。

  | 编号 | 规则 | 检查 |
  |---|---|---|
  | S1 句长 | LRS 一条 R 的条文（去掉代码与括号内容）≤ 80 字；LLD 一个条目 ≤ 200 字、≤ 4 句。超出的拆成子条、表或图 | 致命（字数、句数） |
  | S2 一句一事 | 一条 R 只承诺一件事，一个条目只讲一个机制；并列的情况（「…时…；…时…」）改成条件表或多条 R。一段只讲一个主题、≤ 6 句 | 致命（分号 ≥ 2 或句数 ≥ 3） |
  | S3 描述与程序分开 | R 条文只写行为，不写步骤；步骤写成编号步骤表或流程图，用「做 X」的命令式。一条里不既承诺结果又叙述过程 | 评审 |
  | S4 点名动作者 | 每句的主语是具体模块或外部方（某个子模块、下游控制器、上游）；不用无主句；「被」字句只在动作者不重要时用 | 评审 |
  | S5 一词一义 | 术语表每个概念只用一个词，并加「不用的说法」列；正文出现替代词算违反（例：上游 ≠ 前级；表项 ≠ slot / entry；拍 ≠ beat / 周期） | 致命（按术语表「不用的说法」列） |
  | S6 定语 ≤ 3 层 | 一个名词前的修饰不超过 3 个词组；更长的拆句，或先在术语表定义成一个词 | 评审 |
  | S7 前提与警告的格式 | 对外前提、不采用的做法用固定结构写：表（条件 / 后果，或做法 / 为什么不用，分列），或句式「要求：X。否则：Y」；先条件后后果，理由单列或放解释说明，不混进条文（内部#238，用户 2026-10-06） | 评审 |
  | S8 表代替枚举句 | 一句里并列 ≥ 3 项（去向、取值、情况）的改成表；连续的条件分支改成条件表 | 评审 |
  | S9 上界写数字 | 上界、延时、深度、次数写数字或参数公式（如 `BUF_NUM × (BURST_LEN + 1)` 拍）；「有限、尽快、适当、较少、足够、若干、很快、及时、最终、迟早、无限、一段时间、合理、必要时、尽量」这类词不可检验，不用（内部#253） | 提示（LRS 正文，修订记录与文档信息两节不计） |

  S1、S2、S5 违反一处，fast_check 就输出一行 `路径:行号: S<n> …`，退出码非 0。现有文档清零后由提示转为致命（内部#221）；确有理由保留的，按失败豁免登记，豁免文件是 `flow/check_waivers.yaml`。S9 仍只作「提示」：给处数与前 3 处的文件:行号，不改退出码（用户 2026-10-19 定，内部#221）。
  **计数口径**（唯一以 fast_check 为准，实现在 `scripts/fast_check.sh` 的 `sentence_violations`）：
  - 范围：代码块不计；修订记录与文档信息两节不计（那里是历史改动说明，内部#331）；LRS 只看含加粗 `**R.xxx**` 定义的行、取编号之后的文字（表格行不计）；LLD 的条目是以 `- ` / `* ` / `1.` 开头的列表项与表格的每个单元格（分隔行不算，内部#238）；
  - 先去掉反引号代码与括号（全角「（）」、半角「()」）里的内容，再数：字数 = 剩下的字符数（含标点与空格）；句数 = 「。！？」的个数；分号 = 「；」与「;」的个数；
  - S5 的词表取 LRS 术语一节里表头为「不用」或「不用的说法」那一列，按「、，, /」拆开；正文（去掉反引号代码与链接目标 `](…)`）出现即算。
  - 另两项名字与版本的提示（内部#331）：LLD 反引号里整段是例化名 `U_*` 或寄存器名 `*_r` 的，在本设计树 `rtl/*.v` 里找不到就提示；LLD / param / ppa / timing 文档信息表里「对应 LRS / LLD」一行写的版本不是两份文档当前版本（修订记录最后一行）就提示。
- **多图少字**（用户 2026-10-05）：功能按结构化的小节与表写；场景、序列、按拍行为配图；一条条文超过约 5 行就拆成图加短句。

## 6. 图

- **结构图一律用 draw.io**，LRS 里不用代码块画字符结构图（fast_check 拦：代码块里出现框线或箭头字符即失败）。
  规格描述与解释说明里能用图说明的（数据通路、判断流程、位域与版面、命令序列）尽量配图。
- 框图与场景图用 draw.io 画。源文件 `.drawio` 与导出的 `.svg` 都入库，平放在设计根的 `doc/` 下，不开子目录；
  每个 `.svg` 都要有同名 `.drawio`（fast_check 检查）。PNG 等其他图片格式不放进设计根。
- **画**：用 `flow/doc/figlib.py` 的 `Fig`（`box` / `diamond` / `text` / `edge` / `line` / `title`，`kind=` 取下面配色表的
  ctrl / data / merge / error / intr，`edge(..., kind="data")` 是蓝色数据线），产出与仓里现有图同一形态（`html=0`、未压缩）。
  用法见文件头（内部#227）。
- **导出**（要在 Claude Code 的 Bash 沙箱外跑，沙箱里 draw.io 会挂住）：

  ```bash
  .venv/bin/python3 flow/doc/drawio_export.py designs/<根>/doc/<图名>.drawio    # 同目录出 <图名>.svg；超时杀整个进程组
  ```

  用的是 draw.io 本体（`--no-sandbox`），不是 Homebrew 的 `drawio` 软链（找不到 helper 会挂住）。导出后
  `qlmanage -t -s 1600 -o /tmp <图名>.svg` 转 png 看一眼排版。
- **查重叠**：`.venv/bin/python3 flow/doc/drawio_overlap.py designs/<根>/doc/*.drawio`，图元部分相交就报（容器不算）；
  故意跨边的标签在 style 里加 `kaiwuOverlap=ok`（`Fig.text(..., ok_overlap=True)`）。

- LRS 里用相对路径引用：`![框图](doc/<图名>.svg)`。改了 `.drawio` 就重新导出，两者同一个提交。
- **图号与图注**（内部#137）：每张图紧下面一行写图注 `**图 <章>-<序>** 标题 —— 看什么`（fast_check 检查图片引用的下一个
  非空行以 `**图 ` 开头）；条文引图号，不写「本节的图」「上图」。同一张图在两处引用时只在第一处编号，第二处写「见图 x-y」，
  不再插图。
- **图内标题**：图内第一行写标题，离开上下文也知道讲什么。

## 7. LLD 写作（内部#203）

LLD（`designs/<根>/lld.<顶层>.md`）写「怎么实现」，按模块组织；结构与必填节见模板 `flow/templates/design-root/lld.md`，
机械检查见 `openspec/specs/repo-layout/spec.md`。第 5 节的 S1–S9 与第 6 节的图的规则对 LLD 同样成立。

- **结构**：文档信息 → 概述（含追溯表）→ 框图与模块划分（模块表；小模块另列一张「小模块」表，一行写清功能、所在模块、用到的 CBB，不单开节，内部#239）→ 每个子模块一节
  （功能概述含模块框图 / 接口说明 / 功能描述 / 子模块，递归展开，无则 NA）→ 死锁与冒险（整个设计只写一处）→ DFX → 设计断言。
  顶层主要是连线，用图，不另写顶层功能；每个模块的内容都在它自己的节里，不写「一句话 + 引用」的简写小节。
- **移出 LLD 的内容**：参数化实现（含参数裁剪，如某参数为 0 时整块不综合）写 `param.<顶层>.md`；保层级与面积 /
  关键路径预期写 `ppa.<顶层>.md`；时序原则、切点与时序参数取舍写 `timing.<顶层>.md`。时钟与复位并入时钟门控的描述；
  复用的 CBB 不单列，各模块提一句。
- **不写进 LLD 的内容**：
  - 第 3.1 节的通用前提 / 通用要求编号（P、C）：LLD 与 LRS 一样不写、不引用；只对本设计成立的前提直接写具体内容；
  - 仓库规则与 flow 事项：`params.yaml` 的写法（`deps`、`keep_hierarchy`、叉乘）、`rtl/` 与 `cbb/` 的布局、

  - 过程信息：确认记录（「用户某日定」）、实测现状、「某版本后重量」之类，写进 `doc/track.<顶层>.md`；

  - 简写（`x_*` 一类）必须能在某处展开成全名：顶层端口组可以用一句约定指向 LRS 的接口一章，内部信号组要有表；

## 8. 时序原则（内部#286）

全仓所有 RTL 设计按这一节切流水（用户 2026-10-13 定，从一个设计的 timing 文档提上来）。各设计的 `timing.<顶层>.md`
只写本设计的频率、每拍预算、验收配置、切点与理由，原则引用本节，不重复写。

**预算与级数口径**：
- 每拍的预算按组合单元个数给（N 由各设计按目标频率定，写在它的 timing 文档）。
- 级数 = 一条路径上组合单元的个数，含综合插入的缓冲与反相器，不含起点寄存器的 CLK→Q，也不含终点的 D 或输出端口。
  `make depth` 的 `BUDGET` 按它比；路径报告的行数比它多：寄存器起点多 3，输入端口起点多 2（内部#207）。
- 复位与静态配置输入不计时序。

**怎么切**：
- **参数只有一套**：场景差异靠静态输入定值，综合按取值做 case analysis；只给一种场景用的寄存器级由静态输入选通，另一种场景旁路。
- **CBB 内部的级数视为给定**：只优化 CBB 之外的逻辑，CBB 之外裸露的组合逻辑不超过预算。允许优化 CBB 内部的例外（如仲裁的 `SCHEME` 按时序选）由设计在 timing 文档里写明。
- **尽量少加拍**：先用等价重定时、lookahead、把运算挪到已有的寄存级之前；都不够时才加拍。加拍会改延时的，先改 LRS。
- **打拍只影响时序**：功能正确不依赖打拍配置（第 3 节），所以 TPI 的模式、FIFO 是否直通与深度可以按时序单独调。
- **验证**：等价重定时与挪切点按输出签名逐拍等价验收（`team/roles/kaiwu-design/README.md`「改动的等价证据分三级」的 ①）；加拍的不能比签名，补回归与性能复测。
