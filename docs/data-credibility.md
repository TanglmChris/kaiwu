# 数据可信度与读记录的口径

实验记录（2026-10-25 起每个设计根一个文件 `results/<设计根>/experiments.jsonl`，搬迁见 D-45；
下文写 `results/experiments.jsonl` 的地方指搬迁前的那份单文件）横跨多代流程。这个文件回答一件事：
**手上这条记录能不能这么读。**

它记的都是**不会完结**的知识 —— 哪一批记录因何不可用、哪两批不能放进同一张图、
哪个默认值为什么有意保持次优。这类事实没有完成条件，所以不进 GitHub issue
（issue 的终态是关闭，而关闭会让它们从视野里消失）。需要动手的那一半在 issue 里，
每条 `D-x` 下面都标了对应编号。

分工：**判据**（症状 + 一行检查命令 + 修复）在 `docs/pitfalls.md` 的 P-1…P-18；
**工具与 PDK** 在 `docs/toolchain.md`；**待办** 在
[GitHub issue](https://github.com/TanglmChris/kaiwu/issues)。
本文件的前身是 `FOLLOWUP.md`，迁移对照表在文末。

**每条标题前的标记**（2026-09-21 加，本仓
内部#47）：

- **【降级】** —— 哪批记录因何不可用、哪两批不能放进同一张图。手上那条记录落在
  它的范围里，就要担心。D-1…D-10 那一类。
- **【读法】** —— 某个口径去哪读、凭什么可信、跨某条分界该怎么读。它**不降低**
  任何记录的可信度。D-16（等价证明的覆盖面）是第一条。
- **【降级+读法】** —— 一条里两样都有。D-19 是这样：前五节是降级，后两节是读法。

为什么要这个标记：D-1 到 D-15 全是同一种东西，读者因此可以默认「看见 `D-x`
就是一次降级」——**而这个默认是这份文件好用的一半原因**。读法条目出现之后，
靠每条自己在开头澄清一定会漏，而漏掉的那条会被当成降级读，
**降级读法比真降级更贵：它让人不敢用一批其实没问题的数字。**

编号**保持单一序列、不重排**：编号被引用在提交信息、issue 与各设计的文档里，
重排会让那些引用全部失准。
判断「这条要不要担心」看标记，不看编号。

## 先看这一条：怎么给记录分代

记录带一个 `flow` 段，是由**十项事实**合成的指纹（以 `flow/flow_fingerprint.py` 的
`flow_fingerprint()` 为准）：yosys / OpenSTA / **仿真那一条链** 三个版本 + liberty 内容哈希
+ 综合配方哈希 + STA 配方哈希 + **派生字段的代码哈希**
+ **SS / FF 两角 liberty 的内容哈希** `corner_liberty_sha256`（2026-09-27 起，D-24）
+ **门级仿真用的单元模型哈希** `cell_models_sha256`（2026-10-03 起，D-30）
+ **本设计的配方哈希** `design_recipe_sha256`（2026-10-04 起，D-33；从这一项起指纹按设计算）。
之前各代按引入顺序依次是前七项、前八项、前九项。
**指纹相同才是同一代，才能横向比较。**

⚠️ 反过来不成立：**指纹相同不保证可比**。指纹的事实里**没有一项包含设计 RTL**，
所以改了设计而没改流程时，两代记录会带着同一个指纹并排躺着。
本仓就撞过这种情形（对应本版不收录的 D-14）—— 2026-09-14 两次、2026-09-15 一次，
一共三次，那种情况下判据只能是 `git_commit`，不是指纹。

「仿真那一条链」自 2026-09-14 起指的是**仿真器 + 驱动它的 cocotb**，不只是仿真器
可执行文件：动态功耗由 VCD 反标算出，而 VCD 的内容取决于激励怎么加、时钟怎么走、
波形从哪一刻开始转储 —— 那些由 cocotb 决定。换个 cocotb 版本能改
`sim.total_toggles` 与 `sta.dynamic_power_w`，而 iverilog 一个字节没变（本仓 内部#27
的缺口 3）。**仍然不进指纹的**：`vcdvcd`（解析 VCD 的读数口径）与 `pyyaml`
（决定跑哪组参数）—— 它们目前只被 `requirements.txt` 钉住。

老记录没有 `flow` 段，归入「未知代」，只能按 `git_commit` 再分组
（best-effort，只用于分组，不保证同组就是同一代）。

### 列代与两代配对：一条命令（2026-09-25 起）

```
.venv/bin/python3 scripts/pair_generations.py --list                          # 各代条数、日期、指纹里变了哪几项
.venv/bin/python3 scripts/pair_generations.py --base <前缀> --head <前缀>      # 逐字段配对
```

配对口径固定在脚本里（键、排除哪些字段、配不上的点名、同代重复测量是否一致），
零差异才退出 0。**此后新的【读法】条目引用这条命令与它的结论行，不再手写配对
脚本、不再转述配对表**；下面 D-11 / D-12 / D-13 / D-20 / D-22 里那些配对是在它
之前手工做的，原样保留（脚本对它们复核过：`08e2aa1d ↔ a36146a6` 排除
`synth.sources_sha256` 之后零差异，与 D-21 一致）。

### 第七项：`metrics_code_sha256`（2026-09-14 补）

前六项只覆盖**交给工具的脚本**。那不够：同一份工具输出，换一种解析方式就得到
不同口径的字段，而脚本一个字没变。

**这放过一次真的。** D-6 那个 `critical_path_stages` 虚高 2（把所有 path group
的 cell 行加在一起）是纯解析侧的错，修它的时候是**碰巧**顺带改了 tcl
（加 `-sort_by_slack`）才切开了代。把那次的 tcl 改动撤回、只留 Python 侧的改动：

| | `sta_recipe_sha256` | `metrics_code_sha256` |
|---|---|---|
| 修复前 | `d581f8c009b8` | `9680b7a4638d` |
| 真实的修复（顺带改了 tcl） | `0b049664f974` | `dc584ff6c8d1` |
| 假想：只改 Python 解析 | **与修复前逐字相同** | `e5bfe30e1841` |

第七项覆盖 `flow/flow_fingerprint.py` 的 `METRIC_MODULES` 那七个模块的 **AST**
（判据是「把工具输出变成记录字段，或决定要工具做什么」）。以模块而不是函数白名单
为单位，因为白名单的失效方式是"有人加了新的派生路径却忘了登记"—— 正是它要防的
那件事。模块清单本身也进哈希，所以缩小清单同样分代。

**它不覆盖**：`flow/synth/merge_liberty.py`（产出的 liberty 其内容已单独进指纹）、
`scripts/score.py` 与 `gen_report.py`（只读记录，不写）。

**纯文档改动不分代。** 哈希的是 AST 且显式剥掉 docstring，`ast.dump` 不带行号、
注释根本不进 AST。实测 `9db0feb`（「纠正说法，不动流程」）与 `f881f4e`（纯文档）
在这七个模块上一个都没变。这一条是必须的：如果文档修订也分代，流程代会被噪声
淹没，人就会开始无视代的边界，这项事实也就白加了。

⚠️ **换 Python 大版本会让全部指纹改变**（`ast.dump` 的输出形态随版本变）。
那不是缺陷 —— 解释器就是跑测量代码的那个工具，换掉它与换掉 yosys 是同一类事。
见 内部#25。

**补这项事实的那次重跑顺带证了一件事：这条流程是逐位可复现的。** 那次只改了指纹的
**定义**，没改任何测量代码，所以全部组合的数字理应一个都不变 —— 实测确实如此：
`critical_path_delay_ns`、`area_um2`、`cell_count`、`critical_path_stages`、
`delay_target_ps`、`slack_ns`、`fmax_mhz`、两个功耗字段，以及仿真侧的 `cycles` 与
`total_toggles`，**12 个字段全部 0 个差异**（`cda605a7` → `64b3c318`，
另外六项事实逐字相同）。连带着说明跨代的差异可以归因到流程本身，不是跑两遍的抖动
——**仿真侧也是**，尽管 TB 里有随机激励。

`gen_report.py` 与 `score.py` 默认只呈现最新一代，被排除的条数一律写明，
`--all-generations` 是显式逃生口。

### 可比性来自指纹，不来自参数冻结

这一条决定了本仓的数字**能和什么比、不能和什么比**，而它与上面那套机制是两件事：
指纹管的是「本仓的两条记录能不能比」，管不了「本仓的数字能不能与**外部流程**的
数字比」。

让一批数字之间可比，业界有两条路：

- **冻结参数**：所有设计用同一套固定的综合参数，明确不做 design-specific 优化。
  换来保守、可复现的基线，代价是每个设计报的都不是它能达到的最好值。
  （MoonshotAI 的 nano-kpu 走这条，其 README 也反复声明那不是 signoff 值。）
- **本仓走的是另一条**：`flow/synth/search.py` 在 `DELAY_TARGET_RATIOS` 这组
  delay target 比例上各综合一次，**取最好的那份网表**。让这些数字之间可比的
  不是参数一样，而是**指纹相同**。

三个后果，读记录之前要知道：

1. **`fmax_mhz` 是「在这组比例里能拿到的最好值」，不是电路的物理上限。**
   同一句话对 `delay_target_ps`、以及胜出网表带来的 `cell_count` / `area_um2` /
   `critical_path_stages` 一样成立 —— 它们都是**那一次搜索的结果**，
   由被测对象与搜索范围共同决定。
2. **改搜索策略就是换代，而且是机械保证的**：那组比例已经进
   `synth_recipe_sha256`（与 `YOSYS_TEMPLATE`、`abc.constr` 的内容一起哈希），
   增删或改值都会让全部记录落到新的一代。进指纹的是**比例集合**本身，不是由它
   推导出的每设计皮秒值 —— 后者由各设计自己的基准延时决定，写进去会让每个设计
   自成一代，分代机制就失去意义。
3. **不要把本仓的 `fmax_mhz` 与走固定 recipe 的外部数字直接比** —— 同名，但不是
   同一个量。`calibration/`（本地开源流 vs VCS/DC 参考流的偏差分析，
   内部#6）会直接撞上这一条：
   参考流那一侧通常就是固定 recipe，配对时必须先把两侧的取值口径对齐，
   否则测出来的「偏差」里混着「两个不同的量」。

契约在 `openspec/specs/experiment-trust/spec.md` 的「以搜索得到的最优值报告的指标
必须声明它的取值来源」。

### `hold_slack_ns` 怎么读

这个字段是**域内**（寄存器到寄存器）的最差保持时间余量。三件事必须一起记住，
否则它会被读成别的意思。

**一、它只含 reg→reg，主输入起点与主输出终点的 min 路径被显式排除。**
不是为了让数字好看，是因为那两类的结果由约束里的假设决定，不由电路决定：
本流程用 `set_input_delay 0` / `set_output_delay 0` 建时序环境（它既没有上游也
没有下游），于是「输入在 0 时刻到达」这个假设必然让那些路径违例。

这件事有一个干净的实测证据。2026-09-15 在触发器数相差两个数量级以上的几个设计上取
**不排除**的 `worst_slack -min`，下面是其中 `adder32` 的一行：

| 设计 | 触发器 | `worst_slack -min`（不排除） | reg→reg 最差 | reg→reg 违例 |
|---|---:|---|---:|---:|
| `adder32` | 8 | `-0.021162700663102926` | +0.046633 | 0 |

**所有这些设计上，那个数逐位相同。** 因为最差 min 路径永远是 `rst_n → removal`，而 `rst_n` 按
`sta.ideal_drive_ports` 建模为理想驱动（这个流程不综合复位树，见 D-8），
到达时刻恒为 0 —— 那个数就是库里 DFF 单元的 removal 时间，一个**库常数**，
不说明任何一个电路的性质。全部 min 违例（`adder32` 那一行是 8 条）起点无一例外都是
主输入端口；reg→reg 违例是 0 条。

**二、`null` 不蕴含「没有触发器」。** 缺席的依据是「排除之后还有没有可测的
路径」，不是「有没有时序单元」。单级流水的网表有触发器，但它们只被
`输入端口→reg` 与 `reg→输出端口` 两类路径触及 —— 实测 `adder32 PIPE_STAGES=1`
是 5 个触发器、0 条域内路径。本代 `adder32` 75 条的构成：

| | 条数 | `register_count` | `hold_slack_ns` |
|---|---:|---|---|
| 零触发器（`PIPE_STAGES=0`，含 `CSEL_BLOCK` 曲线 3 条） | 27 | 0 | `null` |
| 有触发器、无域内路径（`PIPE_STAGES=1`） | 24 | > 0 | `null` |
| 有域内路径（`PIPE_STAGES=2`） | 24 | > 0 | 有值 |

**51/75 条是 `null`。** 这不是缺陷，是这批设计的流水太浅的事实。按「有没有
触发器」判缺席的话，中间那 24 条会带着 OpenSTA 的无路径哨兵值
`1.0000000433293989e+39` 落进记录 —— 一个合法的 JSON 数字，会被读成
「余量无穷大」，而且不报错。

**三、`hold_slack_ns > 0` 不等于「hold 没问题」。** 这个数来自 **TT**。
hold 的真实判据是快角：2026-09-27 起（D-24）记录带 `sta.corners.FF.hold_slack_ns`，
看那个；之前各代只有 TT，TT 角为正是必要条件，不是充分条件。

**recovery / removal 不在这个字段的覆盖范围内。** 它们是异步复位**释放**时刻的
检查，而各设计根**都没有复位释放同步器**（全仓 grep 0 命中）。没有同步器时，
`rst_n` 的释放相对时钟沿是任意的，STA 能报出的任何 recovery/removal 数字都只是
在复述约束里假设的到达时刻。这是 RTL 层的事，不是流程的盲区 ——
见 内部#41。
（顺带：recovery 一直在 max 分析里被检查着，它是 max 类检查；从来没被看过的是
min 侧。`knowledge/storage-flow/reset-strategy.md` 里「recovery/removal 没有
检查」那句归因是错的，跟 内部#41 一起改。）

契约在 `openspec/specs/experiment-trust/spec.md` 的「最小延时分析必须只报告设计
内部的路径」与 `openspec/specs/experiment-record/spec.md` 的「记录必须携带域内
保持时间余量」。

## 【降级】D-4. `e00e360` 之前所有记录的面积偏小，宽数据通路设计的延时偏大

**现象**：`flow/synth/synth.py` 调 `abc -liberty <lib>` 时**不带 `-constr`**。
yosys 对 `-liberty` 有两套默认 ABC 脚本（`yosys -h abc` 原文）：

```
without -constr:  strash; &get -n; &fraig -x; &put; scorr; dc2; dretime; strash;
                       &get -n; &dch -f; &nf {D}; &put
with    -constr:  ... 同上 ...; &put; buffer; upsize {D}; dnsize {D}; stime -p
```

不给 `-constr` 就**完全没有缓冲插入，也没有驱动强度优化**。

**后果**：高扇出网络上，一个 `INVx1` 可以硬扛远超它自己 `max_capacitance` 的负载，
一个 cell 就占掉关键路径的一半以上，
而且没有任何工具会报错（`max_capacitance` 在 liberty 里只是声明，
STA 照常外插出一个看似正常的延时）。

**影响面与设计形状强相关**（2026-09-09 实测多个参数组合，下表只列 `adder32` 的三个；
no-constr 一列与当时的记录逐位相符，所以对照的基线就是记录本身）：

| 设计 / 参数 | cells | area | delay |
|---|---|---|---|
| `adder32` RIPPLE/32 P=0 | 96 → 96 | +11.1% | **0.0%** |
| `adder32` RIPPLE/32 P=2 | 160 → 160 | +5.4% | **0.0%** |
| `adder32` KOGGE_STONE/64 P=0 | 898 → 905 | +4.5% | +3.5% |

规律：**面积普遍涨 4~11%**（定尺寸把单元放大），**延时的变化取决于设计里有没有
大扇出网络** —— 小设计不动或略差，有大扇出网络的设计可以是数量级的改善。

**`adder32` 会变成"更大但一样快"，这不是电路变差**。成因是 ABC 的 `upsize` 按
它自己的时序模型放大单元，而本仓库的 STA 环境是输出零负载、输入理想 ——
放大在这个环境里拿不到回报，只留下面积。`KOGGE_STONE/64` 那 +3.5% 同理，
是 ABC 与 OpenSTA 两个时序模型口径不一致造成的抖动，**不是 `set_load` 选错了**：
实测 `set_load` 取 0.1 / 0.5 / 1.0 三档，面积与延时基本相同。

## 【降级】D-6. 2026-09-13 之前所有带流水记录的 `critical_path_stages` 虚高

**结论：`sta_recipe_sha256 = sha256:d581f8c0…` 那一代里，`PIPE_STAGES > 0` 的记录，
`critical_path_stages` 比真实的关键路径级数大 2。同一条记录里的
`critical_path_delay_ns` / `slack_ns` / `fmax_mhz` **不受影响**。**

`flow/sta/run_sta.py` 的 `_count_path_stages` 曾用一个正则扫**整份** `checks.rpt`，
把**所有 path group** 的 cell 行加在一起。而 `report_checks -path_delay max`
默认**对每个 path group 各报一条**最坏路径 —— 这些设计的寄存器都是
`always @(posedge clk or negedge rst_n)`，于是 OpenSTA 会额外打印一条
`asynchronous` 组的 recovery 路径，它贡献 2 行：一行 `rst_n (in)`，
一行 `<ff>/RN`。

这个错法是本仓库最难发现的一种：延时取自 `worst_slack`，是对的；级数多算了两级，
也在合理范围内。**一个错的数字和一个对的数字并排放在同一条记录里**，
没有任何一侧看起来异常。

### 受影响的范围（2026-09-13 实测）

`PIPE_STAGES > 0`（网表里有异步复位触发器）的记录**全部受影响**（当时 `adder32` 有 234 条）；
`PIPE_STAGES = 0`（0 级时一个寄存器都不放，纯组合）的**不受影响**。

**带 `flow` 指纹的那批（`adder32` 73 条）全部属于修复前的 STA 配方**
（`sta_recipe_sha256 = sha256:d581f8c009b855aa…`，实测 73/73），
所以本文件开头推荐用来横向比 PPA 的那一批，它们的 `critical_path_stages`
同样要减 2 才是关键路径本身 —— 只要该记录的 `PIPE_STAGES > 0`。

### 虚高量为什么是 2（2026-09-13 已在真实设计上复核）

| 来源 | path group | 旧口径 → 新口径 | 虚高 |
|---|---|---|---|
| 夹具（OpenSTA 自带 `nangate45_typ.lib`，8 位加法 + 异步复位寄存器） | `clk` + `asynchronous` | 13 → 11 | **2** |
| `adder32` `CLA / PIPE_STAGES=1 / WIDTH=32`（ASAP7 RVT/TT） | `clk`(4.65, 15 行) + `asynchronous`(5.01, 2 行) | 17 → 15 | **2** |

虚高量恒为 2，因为 recovery 路径的形状是固定的：一个输入端口（`rst_n (in)`）加一个
`RN` 引脚，正好两行带两列数字的 cell 行。这也解释了本条开头那个范围判定 ——
`PIPE_STAGES=0` 的网表一个触发器都没有，不产生 `asynchronous` 组，因此**不受影响**。

**交叉验证（72 个 `adder32` 参数组合的逐组对照）**：2026-09-13 在新流程代下把 `adder32` 全量重跑了
一遍（75 条，`flow=82aa726d`）。把它与上一代 `ba10ca69` 共有的 **72 个参数组合**
逐组相减：

| `PIPE_STAGES` | 差值 = 预期 | 差值 ≠ 预期 |
|---|---|---|
| `0`（无触发器，预期差 0） | **23** | 1 |
| `1`（预期差 2） | **23** | 1 |
| `2`（预期差 2） | **23** | 1 |

**69/72 完全符合预期。** 三个例外全都伴随**网表本身发生了变化**
（`cell_count` 和/或 `critical_path_delay_ns` 不同），来自 yosys `0.68+182` → `0.69+24`：

- `adder32 BRENT_KUNG P=2 W=32`：差 1（cells 均为 287，但延时 0.209862 → 0.204855）
- `adder32 CLA P=0 W=32`：差 1（cells 174 → 172）
- `adder32 CLA P=1 W=64`：差 3（cells 414 → 410）

CLA 出现在其中并不意外 —— 它的深度本来就靠 ABC 事后重构，见 `C-1`。

也就是说：**级数口径的修复恰好贡献 2，可测且稳定；偏离全部由网表变化解释。**

> **注意**：这次复核跑在另一台机器上，`flow` 指纹与历史那批不同
> （yosys `0.68+182` → `0.69+24`、iverilog 小版本不同、合并 liberty 的内容哈希

> 但**不等于两批记录可以横向比较** —— 指纹不同就是不同的代，这一点不因为
> 某几个数字碰巧相等而改变。本次复核**没有写入任何实验记录**，产物落在临时目录。

## 【降级】D-7. `fmax_method` 为 `analytic` 的记录，`fmax_mhz` 是「未加时序压力」的值

**结论：`fmax_mhz` 回答的是「在一次*没有给延时目标*的综合里，关键路径恰好有多长」，
不是「这个实现能跑多快」。两者差得到 7%，而且差多少与架构有关。**

`flow/synth/synth.py` 调 `abc` 时不给 `-D`（延时目标）。`yosys -h abc` 带 `-constr`
的默认脚本是

```
… &nf {D}; &put; buffer; upsize {D}; dnsize {D}; stime -p
```

`{D}` 替换成空串时，`upsize` / `dnsize` 以**延时目标 0** 运行 —— 也就是「能放多大放多大」。
这既不是最快的工作点，也不是最小的，只是默认值的副产物。

### 实测（2026-09-13，ASAP7 RVT/TT，260 次综合+STA）

`-D 100` 相对不给 `-D`：

| 组合 | 延时 | 面积 |
|---|---|---|
| `BRENT_KUNG W=32` | **−7.40%** | −5.73% |
| `KOGGE_STONE W=32` | **−5.70%** | −3.82% |
| `BRENT_KUNG W=64` | **−5.83%** | −6.08% |
| `SKLANSKY W=32` | −2.80% | −4.94% |

26 个组合里 8 个两项都更好、9 个延时持平面积更小、8 个变慢（几乎全是 `W=8` 的小电路
与 `CLA`）、1 个无变化。**面积在每一个组合上都变小**，因为 base 就是"放到最大"那一档。

### 这会改变结论，尽管不改变排名

四个位宽下架构顺序都不变。但差距会变：`W=64` 的 `BRENT_KUNG` vs `SKLANSKY`，
不给 `-D` 时 0.3761 vs 0.3800（差 1%，实际是平手），`-D 100` 时 0.3541 vs 0.3690
（差 4.2%）。**顺序没翻，结论翻了。**

### 适用范围

**2026-09-13 流程改成搜索之前**写下的所有记录，全部如此。其中绝大多数的
`sta.fmax_method` 是 `"analytic"`，另有少数（2026-09-04）早于该字段引入、`sta` 段
只有 `slack_ns` 与两个功耗字段。没有任何一条产自加压综合 —— 那时
`flow/synth/synth.py` 的 `abc` 行不含 `-D`，且 `git log -S'-D '` 对该文件零命中。

其后各代（`5d4f715f7…`、`0adea6f6e…`、`cda605a7a…`、`64b3c3183…`、
`06f48f382…`）
**不属于本条**：它们的 `fmax_method` 是 `"search:abc-D"`，是加压搜出来的最好值。

按 `openspec/specs/experiment-record/spec.md` 的定义，这些记录的 `"analytic"` 是
**准确**的：它们确实是未加压下取得的。要的是别把它当成频率上限来读。

**判据不是条数，是字段**：`sta.fmax_method` 为 `"analytic"`（或整个字段不存在）
的记录属于本条；为 `"search:abc-D"` 的不属于。这两种记录**不可横向比较**，
指纹也不同（推导延时目标的那组比例进了 `synth_recipe_sha256`），所以分代机制
会把它们分开。

**已修**：`flow/synth/search.py` 先跑不加压那一档量出该设计的可达延时 `d0`，
再按固定比例 `(1.0, 0.5, 0.3)` 推出三个绝对目标各综合一次，取最好者；
`fmax_method` 用新取值 `"search:abc-D"`，胜出那一档的绝对皮秒记在
`synth.delay_target_ps`。

### ⚠️ `-D` 的死区是一个比例，但「`0.2–0.25 × d0`」这个值只在那 6 个组合上成立

目标给得太紧时 ABC 会**静默**产出与不给 `-D` 逐字节相同的网表，不报错不警告。
2026-09-13 的 6 个组合 × 12 个比例细扫显示，这条边界在 **`0.2–0.25 × d0`**。

> ⚠️ **2026-09-14 收窄了这条推广。** 细扫过的 6 个组合 `d0` 都在几百到两千皮秒，
> 换成相对坐标确实重合。但纯线路重排的电路（`d0` 只有百皮秒量级）
> 上死区一直延伸到 **`1.0 × d0`** —— 原来的比例集 `(1.0, 0.5, 0.3)` 推出的
> 三档目标**整组都落进死区**，护栏触发，那个设计一条记录都写不出来。
>
> 修法是给比例集**加一档 `1.5`**（`DELAY_TARGET_RATIOS = (1.5, 1.0, 0.5, 0.3)`），
> 不是放松护栏。实测这一档不改变既有任何一个组合的胜出者：各设计各取一个组合
> 与 `06f48f38` 逐位比对，网表哈希、延时、面积全部相同。
>
> 所以正确的说法是：**死区是一个比例，但那个比例本身与电路的绝对尺度有关**，

> ⚠️ 护栏**运行时打出来的那句报错**仍写着「实测边界在 0.2–0.25 × d0」，没跟着改。

本文早先写的「阈值是设计相关的 —— `BRENT_KUNG W=32` 在 `≤ 70` ps，

## 【降级】D-8. STA 的边界条件从「理想」改成「与综合一致」

**结论：`critical_path_delay_ns` 现在含输入驱动与输出负载，与此前各代不可横向比较。
影响是一个加性常数（8–25 ps），所以对路径短的实现在百分比上更不利。**

### 改了什么

此前综合与 STA 对同一个电路的边界给出两套假设：

| | 输入 | 输出 |
|---|---|---|
| 综合（`flow/synth/abc.constr`） | `BUFx2_ASAP7_75t_R` 驱动 | 负载 0.5 fF |
| STA（改之前） | **理想**（无限驱动、零转换时间） | **零负载** |

ABC 是照着第一套做单元选择与驱动强度优化的，OpenSTA 却按第二套报数 ——
**优化的对象和度量的对象不是同一个东西**。现在 `STA_TCL_TEMPLATE` 用同一套值。

这改的是**流程内部一致性**，不是「更接近硅」。这个数仍然是 setup-only、单角（TT）、
无时钟不确定度、无 OCV derate、**无线延时**的理想值。

### 实测影响（2026-09-13，当前代的 14 份网表，只重跑 STA）

| 组合 | 只加 `set_load` | 只加 `set_driving_cell` | 两者都加 |
|---|---|---|---|
| `RIPPLE W=64`（1.98 ns） | +0.06% | +0.38% | **+0.44%** |
| `CLA W=64` | +0.99% | +2.09% | +3.08% |
| `SKLANSKY W=32` | +1.19% | +2.76% | +3.95% |
| `KOGGE_STONE W=32`（0.19 ns） | +1.29% | +2.98% | **+4.26%** |

⚠️ **上表取样不足。** 它只覆盖 `PIPE_STAGES=0` 的 `W=32/64`。一次全量重跑显示
真实范围是 **0–15.40%**，最大的是 `adder32 W=8 CSEL PIPE_STAGES=2` ——
路径只有 0.137 ns，同样的 21 ps 就是 15.4%。这恰好印证下一段：

**它是一个加性常数，不是比例项。** 绝对增量 8–25 ps，与路径长度无关 ——
所以百分比效应与路径长度成反比，快电路被加得多。**读跨代百分比时必须记住这一点**：
`KOGGE_STONE W=32` 看起来"变慢 4.26%"，`RIPPLE W=64` 只"变慢 0.44%"，
两者其实被加了同样多的绝对时间。

**六个架构在 `W=32` 与 `W=64` 上的排序完全不变。** `BRENT_KUNG` vs `SKLANSKY`
在 `W=64` 上的差距从 4.24% 微增到 4.67%。**所以这不改变任何已有结论**，
它改变的是这些数字与哪一代可比。

`set_driving_cell` 的贡献是 `set_load` 的两倍多。内部#20
原本只记了 `set_load` 的实测（0.1/0.5/1.0 三档差别不大）—— 那个观察是对的，
但它测的是贡献较小的那一半。

### ⚠️ 这里有一种不会响的错法

tcl 在 `link_design` 之后执行 `set_cmd_units … -capacitance pf`，而 `abc.constr`
的 `0.5` 是 **liberty 自己的单位**（ASAP7 `capacitive_load_unit (1,ff)`）。
把 `0.5` 照搬过去就是 0.5 pF = 500 fF，大 1000 倍：

| | `KOGGE_STONE W=32` |
|---|---|
| `set_load 0.0005`（= 0.5 fF，正确） | 0.2007 ns |
| `set_load 0.5`（当成 pF） | 4.0417 ns（**+1889%**） |

`4.04 ns` 在 5 ns 周期下 **slack 仍然是 MET** —— 照常出报告、照常写记录，
没有任何工具会报错。`tests/test_sta_boundary.py` 因此有两道独立的检查：
两处取值按各自自报的单位换算到法拉后必须相等；边界条件对关键路径的影响必须落在
`(0, 10%)` 内（实测正确配置最大 4.26%，最小的单位错 +194%）。

### ⚠️ 扇出到全部触发器的端口必须按理想驱动建模

第一版把驱动单元加在**全部**输入端口上，于是触发器很多的设计的关键路径变成了这个：

```
Startpoint: rst_n (input port clocked by clk)
Endpoint:   <某个触发器> (recovery check against rising-edge clock clk)
Path Group: asynchronous
   <几 ns>  ^ rst_n (in)     ← 全在这一跳
```

`rst_n` 驱动大量触发器的复位端，实测负载是 `BUFx2` 自己
`max_capacitance`（92.16 fF）的**十几倍**。关键路径因此从
`REG→REG` 的几百皮秒变成几纳秒（延时涨数倍），级数掉到个位数。

**那个数度量的是「这个流程没有综合复位树」，不是电路。** 它与 D-4 是同一类错误，
区别只在于发生在**主输入端口**上 —— 而 `tests/test_synth_electrical.py` 明写
它不覆盖端口。
修法与时钟完全同理（时钟本来就是理想的，因为这个流程也不做时钟树综合）：
设计在 `params.yaml` 的 `sta.ideal_drive_ports` 里声明这些端口，STA 逐端口设驱动
单元时跳过它们。

**这只在特定形态上引爆。** 同一检查在 `adder32` 上不超标：`rst_n`
是 48.1 fF；用**同步复位**的设计，`dfflibmap` 把它映射成不带复位端的
触发器加组合逻辑，复位根本不进触发器的 `RESETN`，负载约等于 0。
（ASAP7 的 17 个时序单元里只有 `DFFASRHQNx1` 带异步复位。）
各设计仍**一律**声明 —— 依据是"这个流程不综合复位树"，与那一档恰好有多少触发器无关。

**绝大多数组合不显形**，只有触发器很多的设计里的少数组合会，其余照常绿。
所以这件事不能靠跑测试发现：`tests/test_sta_boundary.py` 里有一道护栏，
对每个设计逐个输入端口算扇出负载，未被声明为理想而超过 `max_capacitance` 的一律
让检查失败。

时钟端口同样超标，但它按构造就是理想的
（tcl 用 `[all_inputs -no_clocks]`），不在护栏范围内。

### 全量重跑的结果（2026-09-14，`flow=cda605a7`）

相对上一代（同样的加压搜索，但 STA 侧是理想边界）：

| | 第三次重跑（驱动单元加在**全部**输入上） | 第四次重跑（广播端口理想） |

| Δ 延时范围 | 0.00% … 数倍 | 0.00% … **15.40%** |

### C-1. `adder32` 的 `CLA` 分支没有良定义的渐进阶

2026-09-07 位宽扫参发现，**2026-09-09 在修好的流程上复现确认，结论不变**。

`rtl/flat_lookahead.v` 把每一位的进位展开成**完全平铺的与或式**（第 i 位生成 i 个 term，
且 `pacc[j+1] = pacc[j] & p[i-1-j]` 是一条长度 i 的串行与链），naive 规模 O(N²)，
深度全靠 ABC 事后重构。**所以它测出来的「级数」是综合启发式的产物，不是 RTL 的结构性质。**

**决定性证据是跨代一致**（`PIPE_STAGES=0, CSEL_BLOCK=4`，`WIDTH=8/16/32/64`）：

| 流程代 | 延时 (ns) | 级数 |
|---|---|---|
| 2026-09-07（旧代，无缓冲插入、liberty 未修） | 0.2163 / 0.4112 / 0.6977 / **0.5252** | 9 / 14 / 22 / **16** |
| `flow=ba10ca69`（当前代） | 0.1709 / 0.3108 / 0.5377 / **0.4232** | 9 / 14 / 22 / **16** |

64 位比 32 位浅这个反常也原样保留。所以它**不是**电学/缓冲的产物 ——
是 ABC 对那份平铺表达式的结构性重构，在 64 位上走了与 32 位不同的路径。
当前代面积 log-log 斜率 1.214（RIPPLE 1.000、CSEL 1.002），cells 174→584。

**后果**：`CARRY_STRUCT=CLA` 的数字在**单个位宽上**有效（它确实是那个电路的真实测量），
但**不能用来支持任何 O(log n) 的论断**，也不能跨位宽比较。

**不修，有意保留**：`CLA` 这一档的语义就是「把进位交给工具去优化」，
它作为对照组是有价值的。要论证 O(log n) 用 `SKLANSKY` / `KOGGE_STONE` /
`BRENT_KUNG` —— 那三个已于 `8f6e1ba` 加入，并在当前代实测对上理论：
级数每翻倍 Sklansky/Kogge-Stone **+1**、Brent-Kung **+2**，
正是 log₂n 与 2log₂n 的增量。口径写在 `designs/adder32/ppa.ADDER32.md`「关键路径预期」。

### C-4. `SKIP_EXISTING` 对 `adder32` 会全部落空 —— 这是正确行为

它按参数组合匹配，而历史 28 条记录的 `params` 只有 2 个键

### C-6. `sim.cycles` 不是吞吐指标，不许跨设计比

组合 / 短流水、无握手的设计有意义，**同一设计内**看流水深度的影响可以，**跨设计比不行**。

仿真驱动与 `cycles` 的口径要先泛化（吞吐、背压下的有效拍数），**这是那个设计进仓的

## 【读法】D-12. `0c80b2af` 这一代：多时钟支持落地，单时钟测量零变化

**结论：`flow = sha256:0c80b2af0…` 与上一代 `bb11bf398…` 的记录，
除新增的 `sta.clocks` 外**逐字段、逐位完全相同**。这一代可以与
`bb11bf39`、`c4dacda9` 并排读 —— 前提是只读它们共有的那些字段。**

分代是因为**产出记录的代码变了**：`flow/paths.py`、`flow/sta/run_sta.py`、
`scripts/run_experiment.py` 三个都在 `flow_fingerprint.METRIC_MODULES` 里。
本仓 内部#23（`support-multi-clock-sta-constraints`，`e2dc71e`）。

### 改了什么

- `params.yaml` 可以声明**多个时钟**与时钟分组；未声明分组时默认「每个时钟自成
  一组、互为异步」。现有各设计一个 `params.yaml` 都没改 —— 它们走的是
  「未声明 `sta.clocks` 就回退到 `sim.clock_signal`」那条兼容路径。
- STA 逐时钟建约束、逐时钟发输入/输出延时、逐域取最差 slack。
- 记录新增 `sta.clocks`：`[{name, port, period_ns, slack_ns, fmax_mhz}, …]`。
  单时钟设计恰好一项，其 `slack_ns`/`fmax_mhz` 与顶层三个标量**逐位相同**；
  多时钟时标量取**最差的那个域**，所以既有的读取工具（`score.py`、
  `gen_report.py`）不需要先支持数组就能处理多时钟设计。
- 某个时钟域**没有域内路径**时（它的触发器只被跨域路径驱动），该域的
  `slack_ns`/`fmax_mhz` 是 `null` 而不是 0 或周期。

### 比对结果

两代记录按 `(design, params)` 配对，摊平成字段路径逐项比，跳过
`experiment_id`/`timestamp`/`git_commit`/`flow`（每次运行必然不同）与有意新增的
`sta.clocks`。结果：新代记录全部带 `sta.clocks`，**除 `sta.clocks` 外，逐字段差异为 0**
（`adder32` 75 组包含在内）。

### 这一代真正的价值不在这批记录上

这批记录全是**单时钟设计**，它们的数字一位没变 —— 本代的意义是**下一批实验能测
什么**：跨时钟域结构（异步 FIFO 是标准例子）此前**根本量不了**，而那不是
「数字不准」，是这一类实验跑不起来。

⚠️ 顺带修掉三个**只在多时钟下才出现**的静默丢数口子，它们在这批记录上都不成立，
所以**这次的零差异证明不了它们**（判据在 `tests/test_run_sta_multiclock.py`）：

1. **输入/输出延时只绑第一个时钟**，配上异步分组，会让另一个域的 `input→reg`
   与 `reg→output` **整片静默排除**。实测两类路径各 0 条、没有任何警告。
   修法是每个时钟各发一次，第二个起带 `-add_delay`。
2. **不设时钟分组**时，跨异步域的路径被当作真实路径参与 setup 分析。实测
   `worst_slack` 取自一条 `clk_a` 发、`clk_b` 收的路径（0.9233），设了分组之后
   是域内的（4.9233）—— 两个都是 `slack (MET)`、都不报警告、差 5.3 倍，
   而前者不说明电路的任何性质（异步域之间的边沿关系是任意的）。
3. **`find_timing_paths -group_path_count 1` 是每个 path group 各一条**，不是
   总共一条。带异步复位的设计还有一个 `asynchronous` 组（recovery），
   取第一条拿到的不是最差的那条 —— 实测 `adder32` 上逐域报 5.011455、
   顶层 `worst_slack -max` 报 4.815172，差 0.196 ns，两个数都像模像样。

还有一个不属于"丢数"但同样要记的：**同一个 fmax 由两条路算出来会差在末几位**。
顶层走 tcl 里 `period - ws`（全精度相减后 `%.6f`），逐域若在 Python 侧用
「`period` 减已经 `%.6f` 过的 slack」去减，得到 `5410.435648278387` vs
`5410.4356482784`。现在逐域 `arrival` 也在 tcl 里算，与顶层同一个表达式、
同一份全精度值。

### 重跑过程中的一件事

`make sweep` 被 OS 按内存杀掉两次（不是失败，事后 `free -g` 仍有 26 GiB 可用）。
**`SKIP_EXISTING=1` 在换代场景下不能用** —— 它的匹配依据只有参数组合、不含代码
版本，开着它会把上一代的同组合当成"跑过了"，一条都不补。实际用的办法是按
`(design, params)` 对上一代取差集再逐条 `make exp`：它认代，而且逐条跑被杀只丢
一条。这件事已记成本仓 内部#37。

## 【读法】D-16. 等价证明的覆盖面从 2026-09-17 起由 `proved.json` 记账 —— 它不是记录，也不参与指纹

**这一条不降低任何记录的可信度**，它回答的是另一个问题：**「这个设计的等价证明
今天覆盖到哪」该去哪里读，以及那个答案凭什么可信。**放在本文件是因为
「某一档有没有形式化证据」直接决定了那一档的 PPA 数字能被读到多重，
而这件事此前只写在各设计的 `verify.md` 里，改了 RTL 之后没有任何机制逼它跟上。

### 账在哪、记的是什么

`flow/equiv/proved.json`，键是 `<design>::<pair>::{<config>}`，值里有
`proved_at` / `recipe_sha256` / `sources_sha256`。三条判定规则：

| 变了什么 | 后果 |
|---|---|
| 被证的 RTL（`sources_sha256` 对不上） | **该设计**的相关账目失效，要重证 |
| 证明器 `flow/equiv/run_equiv.py` 的任意一个字节（`recipe_sha256` 对不上） | **全部**设计的**全部**账目一次性失效（本仓 内部#39 要的机械信号） |
| 都没变 | 核账 0.05 s 量级，一次 yosys 都不调 |

`proved_at` **不参与判定**，它只为 diff 好读而存在 —— 拿时间戳当判据的话，
「文件变了但时间戳更新」就会变成一条永远通过的护栏，与 D-1 同形。

### ⚠️ 它不是记录，不参与指纹

- **不是 `results/experiments.jsonl`。** 红线 2（只增字段、不回填、不重写历史行）
  管的是记录；`proved.json` 是**当下状态**的账，改 RTL 就该变，重证就该重写。
  两者的写入规则正相反，不要把一个的纪律套到另一个上。
- **不在 `flow_fingerprint` 的七项事实里。** 落地当天实测：指纹仍是
  `sha256:c33181b0…`，`results/experiments.jsonl` 逐字节未动。
  **这条变更不换代、不新增记录。**
- 所以 **账目的状态不能用来判断一条记录能不能读**。判据仍然是指纹 + `git_commit`
  （D-5）。账回答的是「今天这份 RTL 的等价性证到哪了」，
  不回答「当时那条记录跑的是什么」—— 补证是补在**今天的字节**上的，不追溯。

### 它解决了什么

以前 `tests/test_equiv.py` 每次都真跑 SAT，最慢的一个设计就占整套耗时的绝大部分（本仓 内部#42）。
于是压力一直朝「把慢证明标成 opt-in」去，
而 opt-in 的护栏等于没有护栏。账把代价从**每次跑测试**挪到**每次改 RTL 或改证明器**：
整套 `tests/test_equiv.py` 从半小时量级降到**一分钟以内**，用例一条没减，注入反例照样被抓住
（那条走临时目录，源哈希必然对不上，账按设计不拦它）。

契约条款：`openspec/specs/formal-equivalence/spec.md` 的
「等价证明必须记录它证的是哪些字节，证明器自身的改动必须使全部记录失效」
与「等价证明必须报告它这一轮实际覆盖了哪些配置」。

## 【读法】D-18. 多份 RTL 按四条书写约定改写过，**记录一条都没重跑** —— 凭什么说它们仍然可用

**结论先说**：2026-09-20（本仓 内部#46）
按 `openspec/specs/rtl-structure-authority/spec.md` 的四条书写约定改写了多份
RTL，`c33181b0` 这一代的记录**一条都没有重跑**。指纹一位没变
（RTL 不在指纹里，此前已有三次同形，对应本版不收录的 D-14 / D-15 / D-17）。但这一条与前三条
**性质不同**：前三条是「记录不可横向比较，要按 `git_commit` 筛」，这一条是
**「记录仍然可用，不用筛」** —— 而这个结论需要证据，不能靠「我只改了写法」这句话。

### 四条约定改了什么

| 约定 | 性质 |
|---|---|
| 2.3 删掉全部 `` `default_nettype `` | 删指令 |
| 2.5 `localparam integer` → `localparam` | 去类型 |
| 2.4 `wire` 定义与 `assign` 拆开 | 拆行 |
| 2.6 清空 `generate` 内的 `localparam` | 内联 / 上提 |

前两条各自都能改变语义（隐式线网、位宽推导），后两条不能但会大改文本。

### ⚠️ 这个判据的边界：它管综合出来的电路，不管 VCD

**2026-09-21 补**（D-19 第四节实测）：三项齐同证明的是**综合结果**没变，
它**不覆盖 `sim.total_toggles`**。VCD 是 **RTL 层**的产物，改写动了中间信号的
名字与个数，被 dump 的信号集合就跟着变。实测翻转计数改写前后只差了
很小一点。

本条的结论（那批记录仍然可用、不用筛）**不变**：这么小的翻转差换算到动态功耗
远在噪声内，而面积 / 时序那三项本来就被判据钉死了。要改的只是措辞 ——
**「纯语法改写不改变综合结果」是对的，「不改变任何记录字段」是不对的。**
真要用这批记录的 `dynamic_power_w` 做**万分位级**的比较，才需要回头看这一条。

### 判据：`cell_count` + `area_um2` + **去 `src` 属性后**的网表字节，三项齐同

每条约定改完各自比对一次，改前改后各综合一遍。四条全部三项齐同，`diff` 无输出。
覆盖到代表组、极值组与为 2.6 专写的定向组。

**这比等价证明强**：等价只保证功能一样，三项齐同连结构都没动 —— 网表是同一份，
于是**综合出来的一切下游数字（面积、单元数、关键路径、反标功耗）必然也是同一份**。
记录不用重跑，理由在这里，不在「改动看起来无害」。

⚠️ **不能取网表原始字节。** yosys 把 `(* src = "文件:行.列-行.列" *)` 写进网表
（一份网表里有几百处），而四条约定里有三条都在增删行 —— 原始字节
必然全变，而电路一个门没动。第一次比对给的正是这个**假红**，判据因此收窄。
详见 `docs/pitfalls.md` 的 P-9。

⚠️ **三项齐同的判别力被扫参空间夹死。** 落在扫参空间之外的 `generate` 分支，
综合根本不会走到，三项必然齐同 —— 不是因为改对了，是因为没测。2.6 实撞：
某个设计的一份源文件里，一个 `generate` 分支的开关默认 0 且不在 `params.yaml` 里，那条分支
（本批唯一动了位宽语义的地方）
**一次都没被综合到**，所有扫参组的三项齐同对它的判别力是 **0**。补的是
`run_equiv.py` 的对应配对，分支打开后的几档全 PROVED。
**先问「这次改的代码在不在被综合的那几组里」，再看三项齐不齐同。**

### 另一条独立证据：冻结原版仍然等价

`flow/equiv/frozen/` 下留存的参数化之前那份代码的逐字节副本，按本批的 D3
**一个字节没动**。其冻结参考对重证后仍是 PROVED —— 改写后的 RTL 与没被改写过的原版逐位等价。
这一条与网表判据相互独立：前者比的是综合结果，后者比的是 RTL 语义。

### 顺带：为什么这一批把账目全冲了

同一批还改了 `flow/equiv/run_equiv.py`（本仓
内部#49：加 `--ledger`、
输出改行缓冲）。账目的 `recipe_sha256` 哈希的正是这份文件，所以
**全部设计的全部账目都失效**，重证一轮。
账不是记录、不进指纹，详见 **D-16**。

⚠️ 这一轮里「证明器变了」这条失效原因**把「RTL 也变了」盖住了**：失效判定是
短路的，`recipe_sha256` 一对不上就直接判失效，不再去比 `sources_sha256`。
两者同时改时，账目**不能**用来回答「是哪一边变的」—— 它只回答「要不要重证」。

契约条款：`openspec/specs/rtl-structure-authority/spec.md` 的
「RTL 的书写约定，以及『纯语法改写』的判据」。

比对口径：按 `(design, params)` 配对，**覆盖全部共有组合，不抽样**，

结果往哪边走没有道理可讲。这正是 内部#50 说的那件事：yosys 日志明确写着

| 对照 | `total_toggles` |
|---|---|

### 五、配不上的组合，逐类点名

配对不是共有组合配完就完了，两代各有配不上的，必须点名而不是让它们消失在计数里：

- 线宽参数化之前的旧 RTL 批次，`params` 段里根本没有那个新参数的键，所以配对键与本代不同形；
- ⚠️ **有的顶层一条都配不上，而原因不是电路变了，是配对键本身在两代之间不同形。**

  扫参空间变大，上一代的参数键集合与本代永远不相等。

### 六、仿真没过的记录和整组重跑

本代里有一个设计的第一批记录有几条仿真没过：TB 把某个参数写死了

## 【读法】D-20. `08e2aa1d` 这一代：`design` 从小写根名换成大写顶层名，而**换代的原因是 tcl 模板里的三行注释**

**结论先说**：`flow = sha256:08e2aa1d3…` 是这条线上的一代（`ADDER32` 75 条，
75 个唯一参数组合）。它与上一代 `5792722dd…` **逐字段零差异**——
75 组全部配对，每一个测量字段逐条相等。换的只有名字：
`design` 从小写设计根名变成大写被测顶层名。

这一条是**读法**，不是降级：两代的数字一样可信，一样可用。
它要回答的是「同一个电路在记录里有两个名字，怎么读」。

### 大小写映射（一一对应，没有例外）

| 到 `5792722d` 为止的 `design` | `08e2aa1d` 起的 `design` | `design_root`（两代都一样） |
|---|---|---|
| `adder32` | `ADDER32` | `adder32` |

内部#46 的 2.1）。
**目录名一个字母没改** —— `designs/adder32/` 仍是小写，所以 `design_root`
两代相同。根名与顶层名可以不同，是 内部#45 收根买到的能力。

⚠️ **工具不会替你把两个名字接起来，这是有意的。** `score.py` 按 `design` 精确匹配，

要跨这条分界看趋势，只能人工对照上面这张表，并且**知道自己在跨代**。

### 换代的原因：三行注释

规划时的判断是「本变更不换代」——`METRIC_MODULES` 里一个文件都不会被改名改到。
**这个判断错了**，重跑写出来的指纹是 `08e2aa1d` 而不是 `5792722d`。
逐项核对，七项事实里变了两项：

| 事实 | 变没变 |
|---|---|
| `liberty_sha256` / `synth_recipe_sha256` / `yosys` / `opensta` / `sim` | 一个字节没动 |
| `sta_recipe_sha256` | `d675dffa…` → `8b012ca9…` |
| `metrics_code_sha256` | `bf1fbdef…` → `57e0963b…` |

根因是同一处：`flow/sta/run_sta.py` 把 OpenSTA 的 tcl 整段存成一个**普通字符串
字面量** `STA_TCL_TEMPLATE`，而改名脚本把模板内部三行注释里的 `adder32` 改成了
`ADDER32`（例如「实测 adder32 上差 0.196 ns」）。于是
`sta_recipe_sha256`（直接哈希模板文本）与 `metrics_code_sha256`（AST 哈希，
字符串字面量算内容）同时变。

逐文件核过 AST 哈希：**七个 `METRIC_MODULES` 里只有 `run_sta.py` 变了**
（`5a42567125ce` → `59317f02fb2f`），另外六个改的全是注释与 docstring，
AST 哈希逐字未变 —— `flow_fingerprint.py` 的 `_strip_docstrings` 完全按设计工作。
**漏的不是它，是「以字符串形式内嵌的工具脚本，它的注释就是内容」。**

**不改哈希口径。** `flow_fingerprint.py` 的取舍原话是「宁可让『给 abc.constr
加一行』也分出一代 —— 太粗比太细危险得多」，这次正是那条取舍在起作用；
而且改口径本身还要再换一代。判据命令见 `docs/pitfalls.md` 的 **P-13**。

### 凭什么说数字没变：75 组逐字段配对

两代按 `(design 大小写归一, design_root, params)` 配对，**75 组全部配上，
零差异**。判为「必然不同」的只有八项：`design`、`experiment_id`、`git_commit`、
`timestamp`、`synth.sources_sha256`（RTL 字节变了 —— 模块名写在源码里），
以及 `flow` 的 `fingerprint` / `metrics_code_sha256` / `sta_recipe_sha256`。
其余每一个字段 —— `cell_count`、`area_um2`、`critical_path_stages`、
`critical_path_delay_ns`、`slack_ns`、`fmax_mhz`、`dynamic_power_w`、
`static_power_w`、`sim.total_toggles`、`sim.cycles` —— 新旧两代**逐条相等**。

这比 D-18 那次强：那次是「网表三项齐同」的抽查，这次是**全部 75 个组合的
全部字段**。所以「改名不改变电路」在本仓已经是量出来的事实，不是推理。

### 这一代是怎么跑出来的

这批记录横跨多个提交。**横跨多个提交在本仓通常是警告信号**（D-10 就是），这里不是：
它们的 `flow.fingerprint` 完全相同，而指纹覆盖全部测量路径，
所以那些提交之间没有一个动过它 —— 这是算出来的，不是声明的。

扫参第一次**并行**跑（`sweep.py -j 8`，2026-09-21 加），有效并行约 4×。
并行**不可能**改变测量值，理由有三条：
`sweep.py` 不在 `METRIC_MODULES` 里；测量路径上没有任何墙钟依赖（全仓唯一的
`time` 用处是记录的 `timestamp`，cocotb 的 `Timer` 是仿真时间）；每次实验的产物

## 【读法】D-27. 动态功耗的活动率只反标在端口上：内部节点是**传播估算**，结构间的动态功耗排名不能当结论用

> 适用范围：`gate-level-activity`（2026-10-03）**之前**的全部记录。之后的记录改由门级 VCD 反标到内部引脚，见 D-30。

**结论先说**：
- `gate-level-activity` 之前的**全部**记录，动态功耗的活动率都只反标在被测顶层的**端口**上。VCD 来自 RTL 仿真，它的层次名只对得上网表的端口；网表内部节点的活动率是 OpenSTA 从端口**按概率传播**出来的。
- 传播模型看不到**毛刺**（RTL 零延时仿真里本来就没有毛刺，传播模型也不建模），也看不到**真实的相关性**（它假设各输入独立，而激励往往不是，例如 LZD 按 count 均匀分布造激励，高位强相关）。
- 所以**同一设计不同结构之间的动态功耗排名不能当结论用**。文献里结构之间的能量差有相当一部分来自毛刺与节点翻转（Dimitrakopoulos 2008：同延时下低 10–49%），而这正是这个口径看不到的部分。LZD 64 位里动态功耗最低的是 `PRIENC`（5.1 µW，`CLA` 10.2 µW），与文献相反，很可能就是传播模型造成的（内部#65）。
- 同一结构不同位宽之间、同一电路不同周期之间的趋势仍可参考；绝对值只作量级。

### 记录里怎么看出是哪种口径

2026-10-01（`flow-batch-2026-10`）起，记录多一个字段 `sta.activity_annotation`：

| 键 | 含义 |
|---|---|
| `pins` | OpenSTA 报告标注上活动率的引脚数（日志里的 `Annotated N pin activities`） |
| `port_bits` | 被测顶层全部端口的位数之和（取自网表） |
| `scope` | `pins <= port_bits` 时为 `ports`（只标了端口，本条的情形），否则为 `internal` |

这个字段之前的记录没有它，按「未知」读，但按上面的事实，它们都是 `ports`。判据「≤ 端口位数」是偏保守的：误判只会把真反标了内部节点的记录说成只标了端口。

### 要看到内部节点怎么办

零延时门级 VCD 已在 2026-10-03 落地（`gate-level-activity`），见 D-30：`scope` 为 `internal`，与本条的记录**不可横比**。带 SDF 的时序门级仿真（看得到毛刺）**决定不做**：2026-10-03 试验后用户定，代价大于收益，见 内部#84 的试验结论。

| 字段 / 守卫 | 含义 |
|---|---|
| `sim.gate_passed` | 胜出网表的门级仿真是否通过。`false` 时 TT 与两角的动、静态功耗与 `activity_annotation` 都为 `null`，时序与面积照常；RTL 仿真没过时不跑门级，取 `null`。之前的记录没有这个字段 |
