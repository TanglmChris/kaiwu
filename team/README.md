# kaiwu 组织章程

kaiwu 是一个 IP 开发团队：能力（规格、设计、验证、评审、报告）不和某个 IP 绑定，做成仓里的**镜像**；
每个 IP 由自己的项目经理（PM）从镜像拉一组**运行态**会话来干活。契约在
`openspec/specs/team-organization/spec.md`，本文件只写组织层的分工。

```
kaiwu-chief            组织层负责人（常驻）
├─ kaiwu-lead          能力 lead（常驻），维护镜像 team/roles/kaiwu-<能力>/
├─ kaiwu-flow          流程（常驻，全仓一个）
├─ kaiwu-layout        开源维护：开源门禁、开源版文档、公开仓（常驻）
└─ kaiwu-pm-<ip>       每个 IP 一个 PM（常驻）
    └─ kaiwu-<能力>-<ip>   从镜像拉起的运行态会话（每种能力一个）
```

**每个会话只有一个，需要并行就自己拉 subagent**（用户 2026-10-25 定，内部#418）：每个 IP 的每种能力只开一个常驻会话，
组织角色也各只有一个，同能力不再另起 `-sub` 会话。并行时由这个会话拉 subagent，边界见 `team/pull-team.md`「需要并行：本会话拉 subagent」。

## 命名

| 对象 | 写法 | 例 |
|---|---|---|
| 镜像（仓里的文件） | `kaiwu-<能力>` | `kaiwu-design` |
| 运行态会话（keel chat 角色） | `kaiwu-<能力>-<ip>` | `kaiwu-design-foo` |
| 组织角色 | 不带 IP 后缀 | `kaiwu-chief`、`kaiwu-flow` |

没有 `-<ip>` 后缀的名字要么是镜像，要么是跨 IP 的组织角色；运行态会话一定带后缀。

## 协作规则

一个模块（设计）的开发有**五个关键角色**（用户 2026-10-04）：规格、评审、设计、验证，加上所有模块共用的流程；复杂模块另可设一个**可选的项目经理**（用户 2026-10-04，内部#158）。
规格、评审、设计、验证每个模块各一个会话，工作量大时由该会话自己拉 subagent 并行（见 `team/pull-team.md`「需要并行：本会话拉 subagent」，内部#418）；
流程全仓只有一个会话。各方用各自的 worktree，**只经 GitHub 交互**：互不改对方的文件，
不 checkout、不提交对方的分支。规格也在自己的分支提交，评审过了在 issue 里给出定稿提交号，由设计合入设计分支（用户 2026-10-21 定，内部#374：原来规格与设计共用设计分支的例外取消，在制的这一轮做完再切换）。同一分支被两个 worktree 检出时 `.githooks/pre-commit` 拒绝提交。

| 角色 | 会话 | 接入 Slack | 维护 |
|---|---|---|---|
| 规格 | 每模块一个 | 是（管做什么：需求的取舍与变更由用户直接把握） | `lrs.<顶层>.md`、`lld.<顶层>.md`、`doc/`（图与跟踪文档 `doc/track.<顶层>.md`） |
| 评审 | 每模块一个 | 否 | 评审清单 `<设计根>/review/<顶层小写>_review_rN.md` |
| 设计 | 每模块一个 | 否 | `rtl/`、`params.yaml`（`sim:` 段除外） |
| 验证 | 每模块一个 | 否 | `tb/`、`verify.<顶层>.md`、`params.yaml` 的 `tops:<顶层>:sim:`、验证产物（覆盖、问题清单等） |
| 流程 | 全仓一个，所有模块共用 | 否 | 设计根之外的一切（`flow/`、`scripts/`、`openspec/`、`docs/`）；换代与重跑；集成上的答疑（集成本身归验证，内部#213） |
| PPA 报告 | 全仓一个，所有模块共用（用户 2026-10-05，内部#178） | 否 | 不维护代码；产出是记录（只在白名单分支上提交、先提交再记录，内部#422）、报告与数据答复 |
| 项目经理（可选） | 每模块至多一个，复杂、会话多时才由用户设立 | 是（管怎么做、做到哪） | 模块的项目计划 issue（挂在主线 issue 下，例：内部#157） |

（各 IP 的会话名、worktree 与分支见该设计根的 `doc/process.<顶层>.md`。）

**Slack 接入与找用户拍板（内部#180，用户 2026-10-05）**：Slack 是用户掌控项目的通道，接哪些会话按项目结构定（上表「接入 Slack」一列）：
项目经理管「怎么做、做到哪」，规格管「做什么」，这两个接入；设计、验证、流程、PPA 报告、评审都是执行方，不接。
没设项目经理的简单模块，由用户自己决定接哪个会话。
- 没接 Slack 的会话，凡是要用户拍板的事（取舍、口径、范围、优先级），**一律先发给项目经理**：跨会话消息第一行写清问题、附 issue 号，推荐项放最前。
  项目经理汇总后在 Slack 上问用户，答复转回对应会话，并记进相关 issue（写明「用户 <日期> 定」）。改需求的，项目经理转给规格，由规格直接和用户确认。
- 执行方会话用 AskUserQuestion 问，用户不在桌前时可能很久没人回答；能经项目经理问的，不要只在本会话里等。
- **Slack 上要用户知道或决定的消息写 `@owner`**（keel 5.95.3，用户 2026-10-05）：bridge 把它变成真正的 @，Slack 才会推送；
  日常讨论不写，只显示未读。接入 Slack 的会话启动提示里已有这条，开着的会话要 /compact（或 /clear、重开）后才看到。
- **例外**：必须由用户本人在该会话里批准的本地操作（删除文件、推送、其他不可逆操作），别的会话转达的批准不算数；本会话自己的中间产物按 `docs/toolchain.md`「推送、授权与共享资源」的常备授权第 3 条直接删，不在此列。项目经理只能提醒用户去该会话处理，不能代批，也不能让别的会话代做。

**交接两步走（内部#175，用户 2026-10-05）**：issue 是交接记录，跨会话消息是提醒，**两样都要有**。
- 给对方开了 issue（派工、提问题、交接、发布），开完**必须**再发一条跨会话消息，写明 issue 号，提醒对方去看；
  只开 issue、不提醒，交接就**没完成**：对方不会主动轮询 issue。
- 对方处理完、在 issue 里回复之后，也要反过来发消息提醒开 issue 的一方。
- 消息只当提醒，不当交接记录：要求、结论、提交号都写在 issue 里，消息里只放 issue 号和一句话。
- **提醒必须点到名**（内部#429，用户 2026-10-25 定）：私信（`keel chat dm`）、群里写 `@<角色>`、派工用 `keel chat todo --assignee <角色>`
  （对方做完 `keel chat done`，就是回执），或用 `--reply-to` 回复对方那条。只有点到名的消息才会叫醒对方：空闲会话靠信号文件，
  已停的 CLI 会话由 `keel tick` 每次运行时自动恢复。群里不点名的消息谁也叫不醒，不算提醒。
- **等待要登记**（内部#429）：等上游某个提交推上远端，用 `keel chat wait <群> --commit <sha>` 登记，巡检核到就提醒等的一方。
  它只看远端**任何一条**分支含不含这个提交，不看是哪条：等「合进 main」或某条集成分支的，登记了也会提前算满足（10-26 lead 实测），
  这类和「等某个 issue 关掉」一样，现在 `keel tick` 都核不了（等分支是 keel#477，等 issue 是 keel#473），靠上游做完时照上面点名告诉下游。
- **转达仓库状态附命令输出**（design 2026-10-05 的建议，那天 PM 把远端分支的超前落后说反过一次）：说到分支头、本地与远端谁超前、
  某个提交在不在某个分支上时，附上产出这句话的命令和它的输出（如 `git rev-parse --short <分支> origin/<分支>`、
  `git rev-list --left-right --count <分支>...origin/<分支>`），不只转述结论。

**PPA 报告与流程的分工（内部#178）**：流程会话独占改 `flow/`、`scripts/`、`openspec/`，以及换代判断，不再接临时数据请求；跑实验和回答数据只用流程、不改流程，归 PPA 报告会话（`kaiwu-report-<ip>`）。共享资源：
- **CPU**：全机重活（JOBS、`-j`、pytest `-n`）加起来 ≤ 6，由分析、流程、验证共用；大活经 `flow/budget.py` 排队拿 `cpu-heavy`（本仓 worktree 之间排队，别的仓不经这把锁，内部#375；见 `docs/toolchain.md`「跑」的「CPU 预算」，内部#359），谁在跑看 `keel lock list`。全机 CPU 由 kaiwu-flow 兼管（用户 2026-10-19 定）：超了只点名、请对方自己停，不动别人的进程。
- **磁盘**：按 `docs/toolchain.md`「磁盘使用」七条，开跑前查剩余空间、VCD 算完就删、任务结束清自己的 `runs/`。
- **记录**：正式记录只在白名单分支（`flow/record_branches.yaml`：main、各 PM 集成分支、report 分支）上提交、先提交再记录（红线 3，内部#422）；试跑和临时数据不进 `results/`。试跑用 `make -f flow/Makefile exp … TRIAL=1`：记录写到 `runs/trial/<时间>/trial.jsonl`，旁边存当时的 `git status`，不要求工作区干净、不用另建 worktree（内部#222）。
- **交接**：按「交接两步走」，开了 issue 就发消息提醒。
- **共享记忆**（内部#431，用户 2026-10-26 定）：同一仓的所有会话读同一份项目记忆，索引过长会被截断。派工、阶段进度、版本状态不写进记忆，
  放在 issue 与设计根的 `doc/track.<顶层>.md`；关单时属主顺手删掉对应条目。能力经验由 kaiwu-lead 提炼进镜像的「经验」节，
  提炼完通知属主删原条目（lead 不删别人的）。

**项目经理（可选，内部#158）**：简单模块不设，五个角色的分工不变。设了的话：
- **做**：汇聚各会话（规格、评审、设计、验证、流程）正在做的和接下来要做的，尽量让大家同时有事做，发现有会话空等就找能并行的活排过去；维护项目计划 issue（开发完成、功能冻结、代码冻结、PPA 定稿等节点，硬节点由用户定）；向用户汇报状态、计划、风险和要拍板的事。
- **不做**：不写 RTL、TB、规格条文、流程代码；不替用户做技术取舍；不给各会话拉的 subagent 派工（派给会话本身）；不集成（集成归验证）。**推 main 归 kaiwu-chief**（用户 2026-10-20 定，见 `docs/toolchain.md`「推送、授权与共享资源」）；PM 推本 IP 的集成分支（见下面「IP 集成分支」）。
- **交互**：与其他角色一样，经 issue 派工与回报，开完或回复完都要发消息提醒对方（`team/README.md`「交接两步走」）。各角色的节点有滑动风险时，在项目计划 issue 里回报。

**一个设计一个主线 issue**，标签 `design`。主线 issue
**只作汇总**：正文是这个设计的问题索引表，由设计侧在开 / 关问题 issue 时更新；评论里不再提
问题。规格方在
`lld.<顶层>.md` 页首写一行 `主线 issue：#<号>`，两侧据此定位。

**每个问题单开一个 issue**（用户 2026-10-03 定，内部#90），**只读 issue 就能接力**，不依赖任何一方的会话记忆：

- **标签表示归谁处理**：`flow`、`keel`、`design`、`verify`。归 `design` / `verify` 的另加设计根标签，
  名字取设计根目录名（如 `adder32`）。subagent 不单独挂标签，它做的活算在拉它的会话名下（内部#418，取代 内部#283 的双标签做法）。
- **标题**以顶层名开头，如 `<顶层>：…`。
- **正文**第一行写 `主线 issue：#<号>`（GitHub 会在主线 issue 里自动显示回链），其余按下面的模板。
- 流程侧要设计或验证配合的事（改设计根里的文件、迁移文档、交接清单等）也一样单开，打对方的标签；
  不在主线 issue 里提，也不用跨会话消息。
- **实际应用问题先开 `field` issue 再动代码**（内部#261）：凡来自实际应用（冒烟、集成、对照真实对端器件 / CBB）的
  问题，用本 IP 的 `field` 问题模板开（写明现象落到的信号与拍、结构项与参数、RTL 提交、对端行为、波形最小窗口、复现；
  信息不全也照开，模板里「最少要给的」几项有了就行），
  打 `field` 标签，归属标签照旧。内部评审、回归发现的不打。发布范围按 `field` 加功能缺陷筛时，靠的就是这个标签
  （内部#258 曾直接改在 codex 分支上，没开 issue）。

```markdown
主线 issue：#<号>

- 提出：<验证|设计|流程>，分支 `<分支>` @ `<提交>`
- 严重度：<P1|P2|P3>
- 现象：<一两句>
- 复现：`<命令>`（期望 / 实际）
- 依据：`lrs.<顶层>.md` 的需求 R.<编号>（或断言 A<n>）
```

- 严重度沿用验证侧问题清单的 `P1`–`P3`：`P1` 卡住通路（死锁、数据错）、`P2` 行为与规格不符、
  `P3` 规格歧义或措辞。
- 答复写成 issue 下的评论：结论一两句（误读时指出规格原文），改了的写 `<分支>` @ `<提交>`。
- **关闭评论写同类扫查**（内部#250）：修了一处，要扫同类 —— 对称的一侧（读 / 写、请求 / 响应）、
  同一文件里同样写法的其他位置、其他设计根里的副本。关闭评论写明查了哪些位置、有没有同类、同类一并改了
  还是另开了哪个 issue；只写「无同类」不算。内部#249（只问了写响应 `user`，漏了读数据 `user`）与 内部#242
  （内部#220 只改了 A8 / M10，同文件的 A5 / A6 没改）都是只修了一处。
- **关闭由处理方做**：改好、推送、在 issue 里写明提交后关闭，不必等提出方确认（设计侧修好的
  问题由设计侧关闭）；提出方复查不过就重开或另开。`keel/config.yaml` 声明了开本仓
  issue（`issue:`）与关本仓 issue（`issue-close:`，限 `docs/toolchain.md` 常备授权第 2 条：自己名下、证据齐全）。主线 issue 本身不关，随设计长期存在。
- 验证侧没跑完的复测也单开 issue，并在对应的发布 issue 里关联。

## 通用纪律

不属于某一种能力、各会话都会碰到的四个坑。每条写现象、做法和出处。

**1. 发评论链接前，先拿到返回值再发**
- 现象：把「贴评论」和「发消息」放在同一批并行调用里，消息里的评论号是自己编的，两次都得补发更正（2026-10-11）。
- 做法：消息里要带 issue 评论或 PR 链接，先串行贴评论，拿到 `gh api … --jq .html_url` 的返回值再发。手里没有返回值的号，只写 issue 号，不写评论号。
- 出处：内部#361。

**2. gh 写操作报 `Post …/graphql: EOF` 时先复查**
- 现象：`gh issue close 302 --comment …` 输出 EOF，紧接着查 `gh issue view 302 --json state` 仍是 OPEN，评论也没发出去，重试才成功（2026-10-14）。直接报「已关闭」就会错。
- 做法：close / comment / edit 的输出里没有 `✓ Closed` 或评论 URL，就用 `gh issue view <n> --json state,comments` 复查，失败再重试一次。
- 出处：内部#361。

**3. 转达分支领先 / 落后，要附命令输出**
- 现象：只看分支头的提交号，把「远端已包含本地提交、本地少一个提交」说成「远端比本地旧」，对方白做一次推送（2026-10-05）。
- 做法：见上文协作规则「转达仓库状态附命令输出」。判「谁领先」用 `git fetch` 后的 `git rev-list --left-right --count <本地>...<远端>`；判「某提交在不在远端」用 `git merge-base --is-ancestor <提交> <远端>`。
- 出处：内部#361。

**4. 关 issue 的评论里，事实性说法先 grep 核过**
- 现象：关 内部#260 时写「验证侧回归脚本与 fast_check 两个入口都查」，事后 grep 发现只有 fast_check 拦，只能更正并重开；内部#250 把「答复模板」写成「评审与答复模板」（2026-10-13）。
- 做法：关 issue 前对照「要改的 / 验收」逐项在 `origin/main` 上 grep，评论里附命令，不凭记忆写。
- 出处：内部#361。

**IP 集成分支**（用户 2026-10-20 在 PM 会话定，PM 转达）：每个 IP 有自己的集成分支，只有该 IP 的 PM 能推（守卫见 `keel/config.yaml`）。
组员从集成分支拉、做完合回集成分支；只在关键节点（代码冻结、验证出口）由 PM 向 kaiwu-chief 提合入 main 的请求。
kaiwu-flow 等平台侧的更新在组织群 `kaiwu-mgmt` 广播（见下面「keel chat 群」），各 IP 自己把 main 同步进集成分支。
集成分支就是本 team 的 main：正式 PPA 记录与 REPORT 由报告会话在本 IP 的 report 分支上跑、合进集成分支，合 main 只做汇聚、不在 main 上重跑（用户 2026-10-25 定，内部#422；取代 10-20 的「正式记录只在 main 上」）。记录按设计根分文件 `results/<设计根>/experiments.jsonl`。各 IP 的集成分支名见设计根的 `doc/process.<顶层>.md`。

**开源集成分支 `open_release`**（用户 2026-10-25 在 kaiwu-layout 会话定）：内容是 main 加上开源专属的提交（白名单、开源版文档、从公开仓移植回来的修复），只有 kaiwu-layout 能推（守卫见 `keel/config.yaml`）。公开仓只从这条分支上的提交导出，推送前跑完导出验收，每次推送当场请用户确认；layout 定期把 origin/main 合进来，开源专属的提交到节点由 layout 向 kaiwu-chief 提合入 main。公开仓因此可能暂时领先 main；泄漏门禁（fast_check 的「开源集合泄漏不增」）在这条分支上照跑。

**keel chat 群**（用户 2026-10-21 定，起第二个 IP 时）：分两层，不同 PM 不共用一个群。
- **组织群 `kaiwu-mgmt`**：kaiwu-chief、kaiwu-lead、kaiwu-flow、kaiwu-layout、keel 维护（角色 `keel`）和各 PM。平台侧的广播（main 更新、协议刷新、CPU 点名、换代）发在这里，
  各 PM 把与本 IP 有关的转给自己的群。
- **IP 群 `<ip>`**：该 IP 的 PM 和它拉起的会话，组织角色不进。组织角色要找 IP 里的某个会话就私信（`keel chat dm`），点名本来也只有私信叫得醒。
- 新 IP 由 kaiwu-chief 建 IP 群，kaiwu-flow 把新 PM 加进 `kaiwu-mgmt`；组员由 PM 按 `team/pull-team.md` 第 3 步加进 IP 群。
- 例外：第一个 IP 的群建在分层之前，现在还装着组织角色、兼作组织群，迁移另议。
- 巡检按 IP 分（keel 5.193，TanglmChris/keel#434）：`keel/config.yaml` 的 `patrol:` 每个 PM 一项，`scope: group:<ip>`，各 PM 只推动自己群的成员，
  全仓风险归列第一的那个。新 IP 的 PM 开工时由 kaiwu-chief 加一项；巡检由 keel tick（launchd）统一跑，PM 不建主机任务（内部#399）；挂起的 PM 不列。
- 标签路由可以按 IP 分（keel 5.192，TanglmChris/keel#433）：`issue_roles:` 写 `design + <ip 标签>: kaiwu-design-<ip>`，带上 IP 标签的 issue 只发给本 IP 的会话
  （比单标签那条具体，keel 只发给它）。某个 IP 拉起 design / verify 时由 PM 提给 kaiwu-chief 加；没加之前，交接靠「交接两步走」的那条消息。

## 常备授权

只在 `keel/config.yaml` 的 `authorize:` 一处，按 `# 组：<能力或组织角色>` 分组；条目没带 `@<角色>` 的组标「（仅声明）」。
keel 5.170 起（TanglmChris/keel#378）条目可带 `@<角色>` 由 keel 强制，各组改成强制另行处理。本文件不另抄授权表。

## 知识放哪

每类知识的权威出处见 `openspec/specs/knowledge-placement/spec.md`「每类知识必须有单一权威出处」。和组织有关的几条：

- 组织分工：本文件；
- 能力的做法与经验：对应镜像；
- 拉 team 的步骤：`team/pull-team.md`；
- 镜像验收的做法：`team/mirror-acceptance.md`；
- 某个 IP 的事实与进度：该 IP 的设计根与 PM 的项目记忆，**不进镜像**；
- 通用架构知识：`knowledge/`，独立知识库，归 lead 维护。
