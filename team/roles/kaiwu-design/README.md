# 镜像 kaiwu-design：设计

运行态名 `kaiwu-design-<ip>`，每个 IP 一个；要并行就自己拉 subagent（`team/pull-team.md`「需要并行：本会话拉 subagent」，内部#418）。组织分工见 `team/README.md`。

## 职责

管「怎么做」：按定稿规格写设计根的 `rtl/` 与 `params.yaml`（`sim:` 段除外），做时序切分，发布版本。
管共享文件（顶层 RTL、`params.yaml`）、对外发布；拉 subagent 分头改子模块时，审过它们的改动再由本会话提交。

## 输入与输出

- 输入：规格的定稿提交号、派工 issue、验证与评审提的问题 issue。
- 输出：设计分支上的提交、发布 issue（模板 `.github/ISSUE_TEMPLATE/release.md`）、问题 issue 的答复与关闭。

## 交接

- 发布：推送后单开发布 issue，交验证；验证交付回在同一个 issue 里。
- 发现验证没覆盖的情形，单开 `verify` 标签的 issue，不在设计 issue 里顺手提。

## 禁区

- 不跑全量回归、不写顶层端到端 TB（归验证）；发布前只跑关键用例与 `./scripts/fast_check.sh`。
- subagent 不提交、不推送；它的改动没审过不进本方分支。
- RTL 里不写综合指令（`rtl-structure-authority`）。
- 规格问题开 issue 给规格会话，不改 `lrs` / `lld`（见 `team/README.md`「协作规则」）。

## 技能与模板

- RTL 模板：`flow/templates/rtl_module.v`；设计根模板：`flow/templates/design-root/`。
- 发布前必跑与等价证据三级：本文件「设计侧的自测范围」一节。
- 逻辑级数：`make -f flow/Makefile depth`（`docs/toolchain.md`「不写记录地量逻辑级数」）。

## 经验

由 kaiwu-lead 从各运行态会话收集后写进这里，每条写现象、做法和出处（issue 或提交）。举例只用开源设计。
规则本身以出处里指的权威文件为准，这里只记踩过的坑和判断办法。
下文的「回归驱动」指各 IP 验证环境里自己的约束随机回归脚本（公开仓里没有通用版），换成你那个 IP 的回归脚本。出处只写 issue 号；私有仓的提交号不写。

**1. 两个 worktree 共用一个分支，提交前核对索引**
- 现象：另一个 worktree 在同一分支上提交后，本侧 HEAD 前进而索引仍旧。`git add <目录> && git commit` 把整个过期索引写进提交，静默删掉对方 243 个文件；fast_check 和冒烟都发现不了。
- 做法：提交前先看 `git status -s` 与 `git diff --cached --stat HEAD`，只该出现本次要改的文件。看到大批意外删除，或 HEAD 比上次提交前进了，先停下，按「对方最后提交加本侧改动」重建，不要直接提交。规格的改动按 issue 里的定稿提交号合入，不在设计分支上替规格提交（内部#374）；同一分支被两个 worktree 检出时 `.githooks/pre-commit` 会拒绝提交。
- 出处：2026-10-01 一次共用分支的误提交，当天恢复；之后的分支规则见 内部#374。

**2. fast_check 要在最后一个提交之后再跑一遍**
- 现象：为过评审意见改了一处写法（用 `integer` 的改法），带出新的 lint 告警（UNUSEDSIGNAL）；提交前跑的那次 fast_check 在改代码之前，没覆盖到。
- 做法：改动全部提交后，再完整跑一遍 `./scripts/fast_check.sh` 才推送。改动较大的另按本文件「改动的等价证据分三级」做等价证据。
- 出处：内部#215（评审 P3 的批量改写）。

**3. 改声明文件（`params.yaml`、`scoring.yaml`）后 fast_check 之外还要跑 inner pytest**
- 现象：新增扫参参数的 `params.yaml` 改动只跑了 fast_check 就推送，集成时 inner pytest 挂了 3 个：新扫参参数没声明 `role`（`gen_report` 无默认值，缺了就抛错），以及打分基线与声明不一致。
- 做法：改这类声明文件后，提交前再跑 `.venv/bin/python3 -m pytest tests/ -q -n auto -m 'not flow' -p no:cacheprovider`（先 export 工具 PATH，见 `kaiwu-verify` 经验 7）。新增扫参维度时同步声明 `role`，并核对打分基线。
- 出处：内部#206、内部#214。

**4. 审阅意见定下的书写细则要落进 spec，别只留在记忆里**
- 现象：用户审 RTL 时逐条定下的细则（例化就近放、例化名写法等）只记在会话记忆里，与当时 `add-rtl-coding-style` 的 D4 / D7 冲突，两边各写各的。
- 做法：新细则先落进 `openspec/specs/rtl-structure-authority/spec.md` 再照写；写 RTL 前先 grep spec，与记忆冲突以 spec 为准。给 codex / dsh 的任务说明指向 spec，不靠转述。
- 出处：`openspec/specs/rtl-structure-authority/spec.md` 的 D4 / D7 改写与新增的 D28–D35（按 2026-09-30 后的用户审阅意见）。

**5. 新目录的泄漏扫描会空过，「block 0」说明不了任何事**
- 现象：`flow/export/leak_scan.py --ref <分支>` 只扫 `flow/export/manifest.yaml` 白名单里的文件。新构件目录的白名单行由 kaiwu-layout 后加，没加之前照字面跑验收命令，根本没扫新目录，结果照样是 block 0。
- 做法：拷一份临时清单，在 includes 里加上新目录，再用 `--manifest <临时清单> --only '<新目录>/**'` 扫；在 issue 里写明是怎么扫的，不只贴「block 0」。
- 出处：内部#406（一个新构件交付时实测）。

**6. 多级 generate 结构每一级各声明一个向量**
- 现象：压缩树、加法树、链这类多级结构，把所有级拼进一个扁平向量，fast_check 的 verilator lint 报 `UNOPTFLAT`（某个压缩树构件的第一版 15 组参数里 10 组失败），仓里没有 lint 级的豁免。另外，深组合网络里 `always @(*)` 的立即断言在 icarus 下会因 delta 毛刺误报（稳定值全对，仍报几次到几十次），verilator 下 0 次。
- 做法：一开始就按每级一个向量写，在该级的 generate 迭代里声明，下一级用层次名读上一级（如 `GEN_FOR_ROUND[gi-1].word`）；verilator、iverilog、yosys 都认这种写法。组合立即断言的误报在交付时告诉验证方，并写进规格的断言一节。
- 出处：内部#406（该构件规格的「实现要点」与断言一节）。

**7. 写「已采纳」或关单之前，核提交进了集成分支**
- 现象：一个参数改动的提交只推到了特性分支，issue 里写了「已采纳」并关单，两周后才发现它从没进集成分支，之后几次发布的记录都按旧默认值跑。
- 做法：关单或写「已采纳」前跑 `git merge-base --is-ancestor <提交> origin/<集成分支>`（main 上的事用 `origin/main`）。整体复查时，抽出 issue 文本里的提交号，逐个判祖先、比 patch-id，最后按内容核。
- 出处：内部#235、内部#390（复查做法见 内部#390 的评论）。

**8. 交给外部模型实现的 RTL 块要能独立验收**
- 现象：交给 codex / dsh 的块，范围或验收不清，回来后要么和本会话同时改了同一批文件，要么只能凭对方的报告判断对不对。
- 做法：只交规格明确、能独立验收的块（比如能用输出签名证明逐拍等价的重构）。任务说明写明书写约定的出处（经验 4）、改动范围和验收命令。同一 worktree 里不和它同时改同一批文件。回来后自己跑 fast_check、回归和签名比对再提交，它的报告只算一份说法。
- 出处：用户 2026-10-04 定（设计里适合的交给外部模型 CLI）；调用方式见 `docs/toolchain.md`「调用外部模型 CLI」（内部#191）。

**9. 改了子模块，逻辑级数要在顶层复量**
- 现象：子模块单独量 depth 是起点、终点都在本模块里的路径，看不到上层在它前后接的打拍单元和组合段。子模块改完在模块级达标，到顶层仍有终点超预算。
- 做法：改动落在被例化的子模块里时，交付前在顶层按验收用的配置点重跑 `make depth`，按终点报数（kaiwu-report 经验 3）。模块级的数只用来定位，不当验收结论。
- 出处：内部#347。

## 设计侧的自测范围

**设计侧的自测范围**（用户 2026-10-04，内部#149：「设计侧不要跑全量回归，全量回归交给验证；设计回归关键的用例，我们要关注方案和代码」）：

- 设计侧发布前只跑关键用例：改到的模块的单元 TB；修 bug 时，issue 的复现用例在修复前、修复后各跑一次；必要时植入变异，确认检查能抓到错；`./scripts/fast_check.sh`。
- 设计侧不写顶层端到端 TB，不跑全量回归：约束随机全量（回归驱动跑全部配置）与自检 TB 全量（`regress TIER=full`）都由验证在发布流程的第 2、3 步跑（`team/roles/kaiwu-verify/README.md`），结论回在发布 issue 的交付小结里。
- 发布 issue 的「设计侧测试」一栏写明跑了哪些关键用例与结果，不写「全量通过」。
- **端口组合依赖检查，发布前必跑**（io-comb-deps，内部#266，用户 2026-10-11 定 Q4）：在 `params.yaml` 里声明了
  `iodeps_configs` 的顶层，发布前跑 `make -f flow/Makefile iodeps DESIGN=<顶层>`，把汇总贴进发布 issue。
  任一组 FAIL 就不能发布，要么修 RTL，要么由规格在 LRS「接口组合依赖」表里显式允许这一项（写法见
  `docs/spec-writing.md` §3.2）。每组还会报外部耦合下的组合环（io-comb-loops，内部#281，用户 2026-10-12 定）：外部模型是 AXI
  基线（对端的 rdy 可依赖我们的 vld / 数据）加 `params.yaml` 的 `iodeps_loops.rdy_dependent` 声明；按对方整体的环不在
  LRS「允许的接口组合环」表里就判 FAIL，按通道的环只作参考。前缀分不进组的端口要在 `iodeps_loops` 里声明，否则这组 FAIL。
  跑配置之前先查**覆盖**（内部#338，用户 2026-10-19 定）：LRS 表里每个条件段写到的（参数, 取值），以及 `params.yaml` 里名字以 `_EN`
  结尾的开关声明的每个取值，都要至少有一组 `iodeps_configs` 取到（没写的参数按 RTL 默认值算）；缺了就在最前面点名，
  汇总写「覆盖缺口 N」并以非 0 退出，即使每组都 PASS，也不能发布。其余参数的缺口只作提示。补一组配置把那个取值取到即可。
  它不进 fast_check：每组一次 yosys，大设计每组几十秒、几 GB，
  新 worktree 第一次跑还要先算读入集合（大设计几分钟，之后有缓存）；`JOBS` 按内存给。实测数字见设计根 `doc/process.<顶层>.md`。
- **流程仿真用例，发布 / 交付前必跑**（内部#306，用户 2026-10-14 定；内部#304 的教训）：设计根里有流程仿真用例（和 `make exp`
  同一入口跑记录口径流量）的设计，改了 RTL 或流程仿真用到的 TB 后，设计发布前、验证交付前要跑，结果贴发布 / 交付 issue；
  `skipped`（PATH 没带 `~/tools`）不算跑过。各设计的命令与文件清单在设计根 `doc/process.<顶层>.md`。
  inner pytest（`-m 'not flow'`）与 fast_check 都不跑它：热缓存约 15 s + 52 s，RTL 改后第一次要先算读入集合（约 6 分钟）。
- **改动的等价证据分三级**（G3，内部#168、内部#201、内部#210）：① 签名逐作业比对（同种子、同配置，TB 输出逐拍相同；`make -f flow/Makefile sigeq DESIGN=<顶层> OLD=<提交>`，变异体用 `MUTATE='文件::原文::替换'`，内部#224）→ ② 模块级形式等价（改前的模块 ≡ 改后的模块，0 未证；`make -f flow/Makefile revequiv DESIGN=<顶层> TOP=<模块> GOLD=<改前提交> [GATE=<改后提交>]`，GATE 默认当前工作区。先比写法规整后的网表，不同再做时序归纳；每次自带负对照，退出 3 表示方法对该模块不可信。只改注释、空白、内部网名的在 text 级判完，改了表达结构的落到归纳；归纳不证复位的异步性与上电初值，内部#339）→ ③ 会失败的变异体（植入一个错，确认前两级能抓到）。重构、搬家、合并模块至少做 ①②；时序上的等价重定时、挪切点（`docs/spec-writing.md` 第 8 节）至少做 ①，激励要覆盖改动处的定向场景；有意改了行为（如握手时序、加拍）不能比签名的，写明理由，补回归与性能复测（内部#286）。
- **RTL 模块怎么拆**（内部#203 Q3、内部#210，用户 2026-10-05 定）：按两条并列原则——连同子模块的总行数不到 2000 行就把只被它用的子模块并进来；功能独立的模块即使很小也可以保留。存储模型（`memory_models`）与被两个及以上上层共用的模块不并。规则原文只在 `openspec/specs/rtl-structure-authority/spec.md`「RTL 模块按 2000 行拆分」。
- **设计发现的覆盖盲区开 verify issue**（G5，内部#208）：设计侧看到验证没覆盖的情形，单开 `verify` 标签的 issue 交给验证，不在设计 issue 里顺手提。
- **用量额度快用完时交接**（G7，内部#168）：把本地提交（先推到自己的分支）、正在跑的核对、日志位置写进 issue，交下一班（或 PM 安排的会话）接手，不等额度恢复。
- **改了 RTL 的信号名（或删了信号）**：同一个提交里同步改 SVA 的 `bind`，并用回归驱动带上 SVA 跑一次（指定当前设计提交，内部#435）。inner / full 回归不编 SVA，
  改名后照样是绿的；Verilator 把 bind 里找不到的名字当隐式线接成悬空，断言静默失效（内部#194，2026-10-05 一天实撞三处）。
  fast_check 会静态核 bind 连接里的每个名字都在被绑模块里，但它只核名字在不在，核不了接得对不对。
- **SVA 文件的分工**（用户 2026-10-05 定，PM 转）：`bind` 连线（信号名）由改 RTL 的设计侧在同一个提交里同步改，
  并用回归驱动带上 SVA 跑一次；断言内容归验证侧，验证侧在冻结时审 bind 的改动。交付前看回归汇总里 `SVA_HIT` 为 0 的断言：
  上一次发布有命中、这次变 0 的，先查 bind 是否悬空或激励是否丢了，再交付（内部#194、内部#286）。
- **验证分支上核 bind**（内部#211）：验证分支的工作区是 main 上的旧 RTL，被测设计在设计分支、交付后才集成，
  bind 却已跟到被测提交的新信号名。这时给 fast_check（含 pre-push）指定被测提交，被绑模块按那个提交的 RTL 核：
  `SVA_BIND_DESIGN_REF=<被测设计提交> git push`（或 `… ./scripts/fast_check.sh`）。tb/ 下的 SVA 仍读工作区；
  ok 行写明「被绑 RTL 按 <提交>」。设计分支与 main 不给，按工作区核。

## 集成期的过渡端口表（内部#119）

顶层还在逐个并入模块、RTL 端口与最终接口不同时，LRS 只写最终接口，现在的顶层端口写进设计根的
跟踪文档（如 `doc/track.<顶层>.md`），并在 `params.yaml` 声明：

```yaml
tops:
  <顶层>:
    port_doc: doc/track.<顶层>.md   # 集成完成后删掉，端口比对回到读 LRS
```

fast_check 的「spec 端口表与 RTL 一致」随之改读这份文档里的端口表（写法同 LRS），覆盖摘要写明
「集成期 <顶层> 按 <文档>」。跟踪文档里别的表不要同时用「信号 / 方向 / 位宽」三个列名。
