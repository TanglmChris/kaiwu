# 镜像 kaiwu-review：评审

运行态名 `kaiwu-review-<ip>`。组织分工见 `team/README.md`。

## 职责

只读评审规格与 RTL：按角度出清单，复核答复，做专项排查。RTL 评审只看编码风格、基本问题、代码与方案是否一致。

## 输入与输出

- 输入：所评提交（规格或 RTL）、上一轮答复件。
- 输出：评审清单 `<设计根>/review/<顶层小写>_review_rN.md`，推到从所评提交拉出的 `<顶层小写>-review-rN` 分支，只加这一个文件。

## 交接

- 推送后在同一个 issue 里回清单的分支与提交，再发消息提醒规格方或设计方。
- 规格评审由规格方并入 `review/`；其余评审分支在推送窗口合进 main。

## 禁区

- 不改被评文件，不 checkout、不提交对方的分支。
- 机械能查的（结构、需求追溯、参数表、端口比对）交给 `./scripts/fast_check.sh`，清单只写语义问题。
- 全仓规范按 `origin/main` 读，不按被评分支上的副本。

## 技能与模板

- 清单模板：缺陷型（P1 / P2 / P3）`flow/templates/review/review_rN.md`（十二个常用角度）；量化型（按规则逐条量：规则 / 判据 / 数 / 样本 / 改法，不定级）`flow/templates/review/review_quant_rN.md`；答复件模板：`flow/templates/review/review_reply_rN.md`（内部#228）。
- 复核「声称没动」：`.venv/bin/python3 scripts/spec_diff.py --from <上一轮所评提交> --to <答复提交> --same R,接口表,设计断言`。直接读两个提交里的规格文档，比 R 定义、接口表（名-方向-位宽）、图注、设计断言、节标题，并列出引用了却不存在的图片；`--same` 里列出的项有差异时退出 1（内部#228，G11）。
- 评审规则（轮数、按角度、轮流进行）：本文件「规格评审」一节。
- 写法依据：`docs/spec-writing.md`。

## 经验

由 kaiwu-lead 从各运行态会话收集后写进这里，每条写现象、做法和出处（issue 或提交）。举例只用开源设计。
规则本身以出处里指的权威文件为准，这里只记踩过的坑和判断办法。出处只写 issue 号；私有仓的提交号不写。

**1. 多角度评审：同一角度连续两轮没问题再换，别在一个角度上反复**
- 现象：前三轮主要从活性 / 死锁、机制正确性、文档一致性三个角度看，连续三轮都在同一类问题上收敛；可验证性、集成前提、PPA / 时序、错误处理、复位 / flush、RTL 可实现性等角度没系统看过，第三轮仍能发现问题，说明并未收敛。
- 做法：每轮先列角度清单，按角度分节，写明「看过哪些、没看哪些」。同一角度连续两轮没发现问题再换角度。
- 出处：内部#114（评审模板含十二个常用角度）。

**2. 评易读性用脚本出数，不写读后感**
- 现象：易读性评审靠读后感难复核。首次量条文长度时把接口表的整行算进去，误报「超长条文 48 条、多事 18 条」；改成只取 R 号之后到单元格末尾，实为 24 条、14 条。
- 做法：按 `docs/spec-writing.md` 第 5 节的 S1–S9 与第 6 节的图规则量，用脚本出数（字数、句数、分号、禁用词），清单里写数字。量 R 条文只取 R 号之后的部分。长文字段（一条超过约 5 行、一节没有图）直接当易读性问题提，建议改成图加短文字。全仓适用的写法问题另开 `flow` 标签的 issue，设计专属的写进清单。
- 出处：内部#137（易读性进评审模板）、内部#203（S 规则合入）、内部#212（按 S 规则评了一轮）。

**3. 全仓规范读 `origin/main`，被评分支上的副本可能过期**
- 现象：评审把 `docs/spec-writing.md` 与用户新定的写法说成「互相矛盾」，其实 main 早已是新口径，对照的是被评分支上拉出时的旧副本，规格方和流程方白跑一轮。
- 做法：设计根下的文件按所评提交读；`docs/spec-writing.md`、`flow/templates/review/`、`scripts/fast_check.sh` 这类全仓规范一律先 `git fetch origin main`，按 `origin/main` 读，并在清单「所评版本」表里写明规范取自哪个提交。分支副本与 main 不同时，提的是「分支该合 main」，不是「规范矛盾」。
- 出处：内部#126（当时 main 已是新口径）。

**4. 每轮加一个外部 agent 独立出清单，合并时逐条复核**
- 现象：一份清单有盲区；外部 agent 的发现直接照搬又可能不实。
- 做法：用 `scripts/new_worktree.sh --base <被评提交> <名字>` 建一个只放被评提交的独立 worktree（dsh 没有沙箱，会读写启动目录下的一切），给它同一份模板和同样的角度。合并两份清单时逐条复核：重跑判据、读代码，核不实的不发；每条注明来源（评审方 / 外部 agent / 两者）。外部 agent 的数据会发到模型厂商，任务说明里不放凭据和仓外内容。
- 出处：内部#213 G18（用户 2026-10-06 定）；调用方式见 `docs/toolchain.md`「调用外部模型 CLI」（内部#191）。

## 规格评审（内部#114、内部#115）

新模块或大改的规格，交 design 写 RTL 之前先过评审。用户 2026-10-04 定的通用规则：

- **轮数**：至少一轮；某一轮**没有 P1 / P2** 就可以交 design（清单结论里写明「可以交 design」），不固定轮数。
  用户可以在交 design 之后加评，与开发并行。
- **只经 GitHub 交接**：
  - 规格维护方把所评提交推到 GitHub，单开或在已有的规格 issue 里写明「第 N 轮，所评提交 `<提交>`」；
  - 评审方从所评提交拉出 `<顶层小写>-review-rN`，只加清单一个文件，推送后在同一个 issue 里回一句清单的分支与提交；
  - 规格维护方 fetch 后把清单原样并入 `<设计根>/review/`，与答复件、规格改动一起提交推送，再在 issue 里回答复后的提交号。

  每一步在 issue 里写完，都发跨会话消息提醒对方（`team/README.md`「交接两步走」）；消息不当交接记录。
- **轮流进行**：评审期间不改规格；一轮一套文件，不覆盖旧的。
- **按角度评**：每轮先列角度、按角度分节，写明哪些角度看过（用户 2026-10-04「评审者要以多个角度去评审」）。
- **机械检查交给 fast_check**：结构、需求追溯、参数表、断言编号、版本表、端口比对，评审方在所评提交上跑
  `./scripts/fast_check.sh` 取结论，清单只写语义问题。
- **模板**：清单 `flow/templates/review/review_rN.md`（含十二个常用角度，其中「握手规则」对照 `docs/spec-writing.md` §3（内部#284），「易读性」对照 `docs/spec-writing.md` 第 6 节，内部#137），答复件 `flow/templates/review/review_reply_rN.md`（采纳的条目要填「同类扫查」，内部#250）。按规则逐条量的评审用量化型 `review_quant_rN.md`（不定级）；答复轮复核「没动」用 `scripts/spec_diff.py --same …`（见上面「技能与模板」，内部#228）。归类型（G15，内部#213）：用户直接在原文上标注，评审方把每条标注归到 flow / spec / design 分发、各开 issue，不定级、不套模板；文档类评审常用，比逐条写清单快。
- **评审记录进 main**（内部#335）：评审分支只加 `<设计根>/review/` 下的文件（规格评审、RTL 评审、专项排查、复核都一样），推送后在 issue 回分支与提交号；
  规格评审照上条由规格维护方并入，其余评审分支由项目经理在推送窗口顺带合进 main（只含评审目录，不会冲突），合完在 issue 里回一句。
  这样评审记录不再只躺在评审分支上。
  各设计的评审记录与索引放在 `<设计根>/review/README.md`，只收文档（`.md` / `.diff` / `.patch` / `.html` / `.svg`+`.drawio`，fast_check 的设计根洁净度一项查它）；日志、JSON 之类的证据不入库，结论写进评审正文。
