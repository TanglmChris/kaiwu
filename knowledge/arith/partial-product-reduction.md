# 部分积压缩（Wallace 树 / Dadda 树 / 压缩器）

- **类别**：算术单元
- **一句话**：乘法的瓶颈不是"生成部分积"而是"把 n 行加起来"，压缩树用进位保存
  把 n 行在 O(log n) 级内压到 2 行，再交给一次进位传播加法收尾。
- **典型用途**：所有并行乘法器；多操作数求和（MAC 累加、点积、滤波器抽头求和）；
  popcount。

## 结构

n×n 乘法的部分积排成一个高度为 n 的矩阵。直接一行行加是 O(n) 次进位传播，太慢。
关键思路是**进位保存（carry-save）**：不把进位往同一行的高位传，而是把它当成
新的一行留到下一级 —— 于是每一级都没有进位链，延时只有一个全加器。

基本压缩单元：

| 单元 | 输入 → 输出 | 说明 |
|---|---|---|
| 3:2 计数器 | 同权重 3 位 → 和(同权重) + 进位(高一位) | 就是一个全加器 |
| 2:2 计数器 | 同权重 2 位 → 和 + 进位 | 半加器 |
| 4:2 压缩器 | 同权重 4 位 + 进位入 → 和 + 进位 + 进位出 | 见下 |

**每压一级，矩阵高度大约 ×2/3**，所以压到 2 行需要 O(log_{1.5} n) 级，即 O(log n)。
最后剩下的两行（一个"和"向量、一个"进位"向量）用一个前缀加法器做最终的
进位传播加法（CPA）。

两种排布策略的差别只在"每一级压多狠"：

- **Wallace（1964）**：每一级把每列尽可能多的位三三成组压掉，能压就压。
- **Dadda（1965）**：反过来，每一级**只压到刚好不超过下一个允许高度**。允许高度序列是
  `d₁ = 2`，`d_{j+1} = floor(1.5 × d_j)`，即 2, 3, 4, 6, 9, 13, 19, 28, 42…
  从最终的 2 倒推回去，每级只做必要的压缩。

结果是 **Dadda 用的全加器/半加器更少**（因为它从不做多余的压缩），代价是最终 CPA
稍宽一点。两者级数相同。

**4:2 压缩器**值得单独记：它逻辑上等价于两个串起来的全加器，但内部重排后
**关键路径只有 3 级 XOR 而不是 4 级**，而且进位出不依赖进位入（所以横向不会形成
进位链）。更重要的是它让压缩树变成**规则的二叉树**（4→2→…），版图和布线比
Wallace 的不规则三分组整齐得多，这是工业实现偏爱它的主因。

## 关键路径

- 压缩级数：**O(log n)**，n 为部分积行数。具体是把 n 按 ×2/3 缩到 2 所需的级数。
- 每级延时：一个全加器的 sum 路径（约 2 级 XOR），或 4:2 压缩器的 3 级 XOR。
- 最终 CPA：一个约 2n 位的前缀加法器，O(log n)。
- **总计 O(log n)**，对比朴素的逐行相加 O(n)。

一个容易忽略的点：**压缩树的输出到达时间是不齐的**。中间列的位数最多、压得最久，
两端的列早就好了。所以最终那级 CPA 的输入是"中间晚、两端早"，用一个**规则**的
前缀网络是浪费的 —— 值得用不规则前缀网络让晚到的位走短路径。工业乘法器都这么做。

## PPA 权衡

- **Dadda vs Wallace**：Dadda 的压缩单元更少 → 面积和功耗更省；CPA 略宽；
  级数相同，所以延时基本持平。**默认选 Dadda。**
- **4:2 树 vs 3:2 树**：4:2 的级数略优、结构规则、布线好；单个单元比全加器大。
  位宽大时 4:2 通常赢。
- **压缩树 vs 阵列乘法器（array multiplier）**：阵列乘法器是 O(n) 延时但版图极其规则、
  面积小、功耗低、易流水。**位宽小或者可以深流水时，阵列乘法器未必输**。
  不要条件反射选 Wallace/Dadda。
- 功耗上压缩树有个隐性问题：进位保存结构的**毛刺（glitch）很多**，中间节点在一个
  周期内可能翻转多次。这部分功耗静态估算看不出来，**必须靠有真实激励的活动率**
  才能测到 —— 正好是本仓库坚持 VCD 反标的理由。

## 什么时候选它 / 什么时候别用

- **单周期大位宽乘法在关键路径上**：压缩树（Dadda + 4:2 + 不规则 CPA）。
- **可以流水、面积敏感**：先考虑阵列乘法器切流水，或者折叠成多周期。
- **一个常数乘数**：都别用。改用移位加 / CSD 编码，能省掉整个乘法器。
- **多操作数求和（不是乘法）**：压缩树同样适用，而且这是它最被低估的用法 ——
  比如把 8 个数相加，用一棵 CSA 树 + 一次 CPA，远好于 7 次连续加法。
- **popcount**：本质就是一棵纯 3:2 计数器树 —— n 个 1 位数求和，是上一条「多操作数求和」的特例。

## 实现要点与坑

- **写 `a * b` 会让工具自己选实现，你的结构一点都留不下。** 要比较压缩策略，
  必须手写树，并且照本仓库的规矩：压缩单元独立成模块、在 `params.yaml` 的 `keep_hierarchy:` 里声明保层级、
  不要 `-flatten`（见 `docs/pitfalls.md` 的 P-3）。否则 ABC 会从布尔功能重新推导，
  Wallace 和 Dadda 会给出一模一样的网表——这个坑本仓库在加法器上已经踩过一次了。
- **但交付时要反过来想一层。** 接上 Design Compiler 之后，`a * b` 会走 DesignWare 的
  综合乘法器，那是被调优过很多年的东西，**手写树很可能打不过它**。所以正确的做法是
  两个都测：手写树用于理解和拿捏结构，`a * b` 用于交付。别因为手写了就默认更好。
- **符号处理**要和 Booth 编码一起想，不然会在矩阵顶上多出一行符号扩展，白白多压一级。
- **半加器的位置很讲究**：Dadda 的少压缩策略之所以省面积，就在于它把半加器用在了
  刚好需要的地方。照着"允许高度序列"倒推，别凭感觉放。
- **验证时注意毛刺**：功能仿真看不出毛刺功耗，但它是真实的。做功耗对比时激励要
  有代表性（随机 + 典型数据），不能只跑几组定向向量。

## 参数化接口建议

> 接口按本仓 RTL 命名约定写（`rtl-structure-authority`，2026-09-28）：参数 `DAT_W` / `*_W` / `*_N` / `*_EN` / `SCHEME`，端口 `i_` / `o_` 前缀，握手 `i_vld/o_rdy/o_vld/i_rdy`。

```verilog
module PP_REDUCE #(
    parameter ROW_N       = 32,
    parameter COL_N       = 64,
    parameter DADDA_EN    = 1,         // 0 WALLACE | 1 DADDA；二选一写成 _EN（D16）
    parameter C42_EN      = 0          // 0 C32 (3:2) | 1 C42 (4:2)
)(input [ROW_N-1:0] i_col_bits [COL_N], output [COL_N-1:0] o_s, o_c);
```

放进本仓库时，`DADDA_EN` 和 `C42_EN` 做成两个正交的开关，和乘法器位宽
一起扫，正好能量出"策略 × 压缩器"的二维 PPA 面。
