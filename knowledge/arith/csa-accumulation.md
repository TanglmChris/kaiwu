# 进位保存累加与多操作数求和（Carry-Save Accumulation）

- **类别**：算术单元
- **一句话**：把中间结果一直保持成"和 + 进位"两个向量，全程不做进位传播，
  只在最后一次性收口 —— 累加器的时钟频率因此不再受位宽限制。
- **典型用途**：MAC / 点积 / FIR 抽头求和、直方图累加、popcount、
  任何"把很多数加起来"的场合。

## 结构

普通累加器每周期做一次 `acc <= acc + x`，关键路径是一整条 n 位进位链。
进位保存的做法是**不让进位传播**：把累加器拆成两个寄存器 `S` 和 `C`，
每周期只做一次 3:2 压缩：

```
(S', C') = CSA(S, C, x)      // 一个全加器阵列，逐位独立，没有横向进位链
S <= S';  C <= C' << 1;
```

真值 `= S + C`，但这个加法**一直不做**，直到最后需要读出结果时才做一次 CPA。

- 每周期的关键路径 = **一个全加器**，与位宽无关。
- 收口的那次 CPA 用前缀加法器，O(log n)，但只做一次。
- 要一次吃多个操作数（比如 8 个数相加），就搭一棵 CSA 树：
  8 → 6 → 4 → 3 → 2，四级全加器 + 一次 CPA，
  远好于 7 次串行加法。

这和 `partial-product-reduction.md` 里的压缩树是**同一个东西的两种用法**：
那边是一次性压一个矩阵，这边是跨周期反复压。

## 关键路径

- 累加环路：**O(1)**，一个全加器延时（约 2 级 XOR），**与位宽无关**。
  这是它最大的价值 —— 64 位累加器和 8 位累加器跑一样快。
- 多操作数树：压 k 个数需要 O(log k) 级。
- 最终 CPA：O(log n)，只付一次。

对比：普通累加器的环路是 O(n)（ripple）或 O(log n)（前缀），
且**在反馈环路里，没法靠流水线切开** —— 这正是 CSA 累加不可替代的原因。

## PPA 权衡

- **性能**：巨大提升。累加环路从 O(log n) 降到 O(1)，而且因为是反馈环，
  流水线救不了它，只有 CSA 能救。
- **面积**：寄存器翻倍（S 和 C 各一份），加一个全加器阵列，再加最后的 CPA。
  对宽累加器来说这个代价通常很值。
- **功耗**：多一份寄存器 → 静态功耗和时钟树功耗上升；但没有长进位链
  → 毛刺显著减少，动态功耗可能反而下降。**净效果要实测**。

## 什么时候选它 / 什么时候别用

- **累加器在关键路径上、且是反馈环**：几乎必选。这是教科书答案。
- **要连续做很多次加法，中间结果不需要读出**：选。
- **每个周期都要读出真值、或者要做比较/判零/溢出判断**：**别用**，见下面的坑。
- **只加两个数**：不适用，直接用前缀加法器。

## 实现要点与坑

- **carry-save 形式下没法直接比较大小、判零、判符号。** 这是最常见的翻车点。
  `S + C == 0` 不等于 `S == 0 && C == 0`。任何需要判断数值的逻辑都必须
  先过 CPA —— 如果你的设计每周期都要判一次，CSA 的优势就没了。
  （有专门的 carry-save 判零电路，但它本身就有 O(log n) 的代价。）
- **溢出判断同理**，要么留足位宽让它不可能溢出，要么付 CPA 的代价。
- **`C` 的移位别搞错**：进位的权重比和高一位，寄存时要左移一位，
  最高位的进位就是溢出。
- **结构会被综合抹平**：功能上 `S+C` 就是一个加法，不在 `params.yaml` 的 `keep_hierarchy:` 里声明保层级
  的话综合可能把你的 CSA 结构重组掉（见 `docs/pitfalls.md` 的 P-3）。
- **位宽要留够**：累加 k 个 n 位数需要 `n + ⌈log₂k⌉` 位。

## 参数化接口建议

> 接口按本仓 RTL 命名约定写（`rtl-structure-authority`，2026-09-28）：参数 `DAT_W` / `*_W` / `*_N` / `*_EN` / `SCHEME`，端口 `i_` / `o_` 前缀，握手 `i_vld/o_rdy/o_vld/i_rdy`。

```verilog
module CSA_ACCUMULATOR #(
    parameter DAT_W      = 32,
    parameter OPND_N     = 1,          // 每周期吃几个操作数
    parameter CPA_SCHEME = 3           // 收口用哪种加法器；原文只写 PREFIX，编号沿用 ADDER32 的 SCHEME 是 2026-10-01 的推论：3 SKLANSKY | 4 KOGGE_STONE | 5 BRENT_KUNG
)(input clk, rst_n, i_en, input [DAT_W-1:0] i_x [OPND_N],
  input i_rd, output [DAT_W-1:0] o_dat, output o_vld);
    localparam CPA_SCHEME_SKLANSKY    = 3;
    localparam CPA_SCHEME_KOGGE_STONE = 4;
    localparam CPA_SCHEME_BRENT_KUNG  = 5;
```

本仓库落地时，最有说服力的对比是**同一个累加器的两种实现**（普通 vs CSA）
在**位宽扫描**下的 fmax 曲线：普通实现的 fmax 随位宽下降，CSA 的应该basically 平。
这个对比图比任何文字都能说明问题，而且正好用得上已经打通的 sim→synth→STA 链路。

## 出处

进位保存加法没有单一原始出处，它随早期计算机算术一起成型
（可追溯到 1950 年代的乘法器设计）。系统论述见计算机算术教科书
（Parhami《Computer Arithmetic: Algorithms and Hardware Designs》
讲多操作数加法的章节）。压缩树部分的一手文献见
[`partial-product-reduction.md`](partial-product-reduction.md) 的 Wallace / Dadda。

## 本地实测

暂无。**这张卡建议优先实现** —— 理由：它不依赖乘法器，改造成本低，
而"fmax 随位宽的曲线"是个非常干净的实验，能同时验证本仓库的 fmax 测量
是否可信（普通累加器的 fmax 必须随位宽单调下降，如果没有，说明流程有问题）。
