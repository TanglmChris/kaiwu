# knowledge/ 写作约定

RTL 结构选型的知识沉淀，四类：`arith/`（算术单元）、`storage-flow/`（存储与流控）、
`priority-encode/`（优先级与编码）、`arch-technique/`（架构范式与技巧）。
模板、写作约定和覆盖计划都在 `knowledge/README.md`，写新卡片前先读它。

三条硬约定，**不要破坏**：

1. **卡片只放结论和方法，不放实验数据。** 数据在实验记录 `results/<设计根>/experiments.jsonl`，
   两边靠卡片末尾固定的「本地实测」一节挂钩（填 `experiment_id`）。没跑过就留空，
   不填猜测值。
2. **出处必须核实过才写。** 编造的参考文献比没有参考文献更坏。核不到公开出处的，
   就写明"未核实，引用前自行确认"。
3. **凡是靠结构而非功能取胜的电路，卡片里必须写明比微架构时要保住它的层级。**
   这是本仓库踩过的坑（见 `docs/pitfalls.md` 的 P-3），前缀加法器、压缩树这类电路
   功能上等价于 `a+b` / `a*b`，不设边界的话综合会把结构差异抹平。保层级在该顶层
   `params.yaml` 的 `tops:<顶层>:synth:keep_hierarchy:` 里声明，不写在 RTL 里，也不是每个设计都强制
   （P-15，2026-10-05 起，内部#216）。

还有一条贯穿全库的测量边界，写在 `knowledge/README.md` 里、这里再强调一次：
**本地流没有 LEF / 没有布局布线 / 没有寄生参数，连线代价恒为零**，所以会系统性
高估"用连线换级数"的结构（Kogge-Stone 是典型）。这类结论在 DC / P&R 到位前
都要打问号。
