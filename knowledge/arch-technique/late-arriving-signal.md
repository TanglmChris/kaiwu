# 晚到信号后置（Late-Arriving Signal）

- **类别**：架构范式与技巧
- **一句话**：找出到得最晚的那个输入，**重构逻辑让它只穿过最后一两级门** ——
  同样的功能、同样（或略多）的面积，关键路径直接短一截。
- **典型用途**：ALU 的 carry-in / 操作码、
  cache 的 way-select（tag 比较结果到得晚）、
  仲裁 grant 送到数据 mux、
  跨模块来的 stall / flush / ready、
  任何"从很远的地方来的一根控制线"。

## 结构

### 核心观察

关键路径 = **到达时间最晚的输入** + **它到输出还要穿过的级数**。
优化前者（把信号变早）通常做不到（它来自别的模块）；
优化后者是 RTL 作者能做的事。

```
坏：  y = ((late & a) | b) & c | d        // late 在最深处，穿 4 级
好：  y = late ? f1(a,b,c,d) : f0(a,b,c,d) // late 只穿 1 级 mux
```

后者就是[预计算](precompute-lookahead.md)：**把晚到信号推到 mux 的选择端。**
这两张卡是同一件事的两面 —— 这张说"为什么要做"，那张说"怎么做"。

### 四种常用手法

1. **推到 mux 选择端**（预计算）。最有效，代价是复制逻辑。
2. **重结合（reassociation）**。`(a op b) op late` 已经是好的；
   `late op (a op b)` 在树形结构里可能被排到深处。
   **AND/OR/XOR 树里，把晚到的叶子放在离根最近的位置。**
   加法树同理：`(x+y+z) + late` 比 `late + x + y + z` 的
   朴素左结合展开要好。
3. **复制逻辑缩小锥体**。让晚到信号只驱动一个很小的逻辑锥，
   把它扇出到的其他地方换成早到信号的副本。见
   [`logic-replication.md`](logic-replication.md)。
4. **把它移到下一拍**。如果时序允许加一拍延迟，
   这是最彻底的办法（也最省面积）。**先问能不能加拍，再想怎么优化组合。**

### 反过来：早到信号前置

对偶的技巧同样有用。如果某个输入到得特别早（比如一个常年不变的配置寄存器），
就该让它穿过尽量多的级 —— 把它的影响提前折叠掉。
**配置位应当尽早参与逻辑，控制位应当尽晚参与逻辑。**

## 关键路径

这张卡就是关于关键路径的，没有额外的渐进阶要写。要记的是一条判据：

> **重构值不值 = (省下的级数) × (每级延时) 减去 (新增 mux 的延时和面积)。**
> 省 1 级去换一个宽 mux，通常是亏的；省 4 级才有意思。

## PPA 权衡

- 手法 1（预计算）：面积成倍，见
  [`precompute-lookahead.md`](precompute-lookahead.md) 的实测。
- 手法 2（重结合）：**面积几乎不变**，是四种里最便宜的一种。
  应该优先试。
- 手法 3（复制）：面积增加与复制的锥体大小成正比。
- 手法 4（加一拍）：面积**减少**（不用复制），代价是延迟 +1 拍
  和一整套控制/反压的改动。

## ⚠️ 本仓库测不出这张卡（2026-09-07 核实）

两个独立的原因，都要说清楚：

1. **STA 侧：`flow/sta/run_sta.py` 写的是**

   ```tcl
   set_input_delay  0 -clock clk [all_inputs -no_clocks]
   set_output_delay 0 -clock clk [all_outputs]
   ```

   **所有输入被假定在时钟沿同时到达。** 这等于宣布"没有晚到信号"，
   于是这张卡描述的问题在本地的 STA 报告里**根本不存在**。
   要观察它必须给某个输入设一个非零的 `set_input_delay` ——
   那是改 `flow/**`，按 `CLAUDE.md` 要走 keel Full 模式。

2. **综合侧：ABC 只有整体延时目标，没有逐输入的到达时间**。fmax 搜索会给
   `abc -D` 加延时压力，但 `flow/synth/abc.constr` 只设驱动单元和负载，不设
   `set_input_delay`（「改 STA 周期网表不变」推不出「综合不是时序驱动的」，见
   `openspec/specs/experiment-record/spec.md` 的对应 Scenario 与 `flow/sta/run_sta.py` 开头的说明）。
   ABC 拿不到输入到达时间，**它没有任何信息去判断哪个输入晚**，
   所以不可能自动做后置优化。DC 会（它读 `set_input_delay`
   并据此做时序驱动的结构选择）。

**结论：在本仓库里，晚到信号的优化 100% 是手工的，
而且优化了也测不出来。** 这不是"效果小"，是"测量装置里没有这个量"。

这条对 `calibration/`（本地 vs 参考工具流的偏差分析）很有价值：
**它是一个可以预言的偏差来源** —— 同一份 RTL，DC 会因为知道输入延迟而
重构逻辑，yosys 不会。等 DC 接上，这应当是最早去验证的几条之一。

## 什么时候选它 / 什么时候别用

- **STA 报告里关键路径的起点是一个输入端口或一个远处模块的输出** →
  先看这张卡。
- **关键路径完全在本模块内部的寄存器之间** → 晚到信号不是问题，
  去 [`pipelining.md`](pipelining.md)。
- **能加一拍** → 加拍，别做组合重构。**这是最常被跳过的第一选项。**
- **省不到 3 级** → 大概率不值得复制逻辑。
- **在本仓库里想量化收益** → **现在不行**，见上。

## 实现要点与坑

- **"哪个信号晚"必须来自 STA 报告，不能靠猜。** 凭直觉重构逻辑
  是这张卡最常见的浪费 —— 改完了关键路径没变，因为猜错了。
  本仓库的报告在 `runs/<experiment_id>/sta/` 下。
- **重构必须保持功能严格等价。** 手法 1 和 3 都在复制逻辑，
  复制出来的两份很容易在边界条件上分岔（溢出、符号、复位值）。
  **改完要跑等价性检查** —— 而本仓库现在没有网表等价性检查
  （见 内部#22），所以这类改动在本地是**无保护**的。
- **综合工具会把你的重构还原回去。** 这是最讽刺的一条：
  你辛苦推到 mux 选择端的结构，ABC 的 `&dch` 从布尔功能重新推导时
  可能又摊平了。**要保住重构就要在 `params.yaml` 的 `keep_hierarchy:` 里声明保层级**
  （`docs/pitfalls.md` 的 P-3）。而一旦设了边界，工具在边界内的优化空间也小了 ——
  这个矛盾在 [`retiming.md`](retiming.md) 里也出现过，
  是本仓库"结构保真 vs 工具优化"的通用张力。
- **别为了后置晚到信号而把早到信号变晚。** 常见的失误是把 mux 塞进去之后，
  两条预计算的路径各自变长了一级，净收益为负。
- **跨模块的晚到信号，正确的修法往往在对面。** 如果 `ready` 从下游
  组合地传上来，与其在本模块重构，不如在下游插一个
  [`../storage-flow/skid-buffer.md`](../storage-flow/skid-buffer.md)
  把这条组合路径切断。**先看能不能在源头解决。**

## 参数化接口建议

> 接口按本仓 RTL 命名约定写（`rtl-structure-authority`，2026-09-28）：参数 `DAT_W` / `*_W` / `*_N` / `*_EN` / `SCHEME`，端口 `i_` / `o_` 前缀，握手 `i_vld/o_rdy/o_vld/i_rdy`。

这张卡描述的是重构手法，不是可参数化的结构。要做实验的话，
载体应当是一个**故意造出晚到信号**的设计：

```verilog
module LATE_DEMO #(
    parameter DAT_W  = 32,
    parameter SCHEME = 0         // 0 NAIVE（late 在最深处） | 1 MUX（推到选择端） | 2 REASSOC（重结合）
)(
    input  [DAT_W-1:0] i_a, i_b, i_c,
    input              i_late,   // 约束里给它一个大的 set_input_delay
    output [DAT_W-1:0] o_dat
);
    localparam SCHEME_NAIVE   = 0;
    localparam SCHEME_MUX     = 1;
    localparam SCHEME_REASSOC = 2;
```

但**这个实验需要先改 `run_sta.py` 支持按端口设 `set_input_delay`**
（keel Full 模式）。在那之前建不起来。

## 本地实测

**暂无，而且当前流程下做不了** —— 见上面的两条原因。
这是整个知识库里**唯一一张"技巧本身有效、但本地测量装置里没有对应物理量"的卡**，
所以它的正确用法是：

1. **现在**：当成 code review 的检查项（看 STA 报告的路径起点），
   不当成实验课题。
2. **接 DC 之后**：它是 `calibration/` 的优质素材 ——
   同一份 `SCHEME = NAIVE / MUX` 的 RTL，
   **本地流应当测不出差别，DC 应当测得出**。
   这个"预期偏差"本身就是一条可验证的假设，比事后解释偏差有价值得多。
