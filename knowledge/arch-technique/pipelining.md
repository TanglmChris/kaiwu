# 流水化（Pipelining：cut-set 与级平衡）

- **类别**：架构范式与技巧
- **一句话**：在前馈组合图上画割线、割到的每根线插一个寄存器 —— 换来的是
  **吞吐和 fmax**，赔进去的是**延迟、面积和一份寄存器固定开销**；
  切得不均匀就等于没切。
- **典型用途**：几乎所有吞吐受限的数据通路 —— 加法器/乘法器、
  滤波器、协议引擎、排序网络、任何"每拍来一组数"的场合。

## 结构

### cut-set 定理

把组合逻辑看成有向图。**画一条把输入侧和输出侧完全分开的割线，
在割线穿过的每一根线上插入一个寄存器，功能不变、延迟 +1 拍。**
前提两条：

1. **图是前馈的**（无反馈环）。有环的话环上的寄存器数不能随便改 ——
   那是 [`retiming.md`](retiming.md) 和
   [`parallel-unroll-cslow.md`](parallel-unroll-cslow.md) 的地盘。
2. **割线要"全割"**。漏掉一根跨越的线就是功能错误，而且这种错误
   在短激励下往往测不出来。

### 级平衡才是全部

```
T_clk = max(每一级的组合延时) + t_setup + t_cq + 时钟不确定度
```

注意是 **max**，不是平均。切成 N 级但有一级特别长，fmax 就由那一级决定，
其余 N−1 级的寄存器纯属白付面积。**流水化的工作量九成在"切在哪"，
不在"怎么插寄存器"。**

### 寄存器开销给出深度上限

组合总延时 D，切成 N 级，每级开销 `t_ovh = t_setup + t_cq`：

```
T_clk ≈ D/N + t_ovh
加速比 = D / (D/N + t_ovh)  ——> 上限 D / t_ovh
```

**N 趋于无穷时加速比不是无穷，而是 `D / t_ovh`。** 当每级组合延时降到
和 `t_ovh` 同量级时，再切一刀几乎没有收益，只有面积和功耗的代价。
这就是"流水到几级为止"的判据。

> ⚠️ **上面那个 `D/N` 藏了一个假设：延时随规模线性增长。**
> 只有 O(n) 的结构（行波进位链）才满足它 —— 位宽减半、延时减半。
> 对 O(log n) 的前缀加法器，位宽减半只减掉一级左右；
> 对 O(√n) 的 carry-select 介于两者之间。
> **所以"切成 N 段就该快 N 倍"只对慢结构成立**，
> 拿它当所有结构的基准会得出错误的"效率损失"结论。
> 正确的基准是 `delay(WIDTH/N) / delay(WIDTH)`，即该结构自己的位宽-延时曲线。
> 本仓库的实测把这一条量出来了，见下面的「本地实测」。

## 关键路径

- 目标：把 **O(D)** 变成 **O(D/N + t_ovh)**。
- 实际达不到 D/N，因为 (a) 逻辑的切点是离散的，切不出恰好相等的几段；
  (b) `t_ovh` 是每级都要付的常数。本仓库实测的效率是 **74%~79%**（见下）。

## PPA 权衡

- **面积**：每级 + W 个触发器。ASAP7 里一个 DFF 比一个 FA 大，
  **32 位宽的一级流水寄存器不是小数目**（本仓库实测的每级面积增量见下）。
- **延迟（latency）变差**：N 级流水的结果晚 N 拍出来。
  **流水提高的是吞吐，不是延迟** —— 这是最常被搞混的一点。
- **功耗**：触发器多了、时钟树大了，动态功耗上升；
  但组合逻辑的毛刺传播被寄存器截断，这部分反而下降。净效应要实测。
  ⚠️ **本仓库当前测不了**：功耗反标是坏的（`docs/data-credibility.md` D-1）。
- **本地流不会帮你做流水**（2026-09-07 核实）：yosys 0.68 的 `synth`
  **没有 `-retime` 选项**，而且 `flow/synth/synth.py` 里调的是
  `abc -liberty`（**没有 `-dff`**），ABC 根本看不到触发器。
  **所以流水级切在哪 100% 由 RTL 决定，工具一刀都不会帮你挪。**
  接了 DC 之后这条会变（DC 默认做 retiming），届时同一份 RTL 的结论会不一样。
  详见 [`retiming.md`](retiming.md)。

## 什么时候选它 / 什么时候别用

- **吞吐/频率受限** → 流水。这是它唯一的用途。
- **延迟受限**（比如一条要在 1 拍内闭合的控制环）→ **别流水**，会更糟。
- **有反馈环** → 环上不能自由插寄存器，先看
  [`retiming.md`](retiming.md) 的 iteration bound；要突破就得
  [`parallel-unroll-cslow.md`](parallel-unroll-cslow.md) 的 C-slow。
- **每级组合延时已接近 `t_setup + t_cq`** → 停手，再切是纯亏。
- **面积紧、吞吐够** → 反过来做 [`folding-time-multiplex.md`](folding-time-multiplex.md)。
- **数据不是连续流**（每 100 拍来一组）→ 流水的吞吐收益等于零，
  只剩延迟和面积的代价。**先看利用率再决定。**

## 实现要点与坑

- **控制信号必须和数据一起流水。** `valid` 晚一拍或早一拍就是错拍，
  而且在"连续满载"的激励下常常看不出来（每拍都 valid，错拍不可见）。
  **必测用例：单拍脉冲 + 稀疏 valid。**
- **反压是流水化的第二半，不是可选项。** 加了 N 级流水就要能停 N 级。
  全局 enable（stall 链）会形成一根扇出巨大、跨越整条流水线的长线，
  它本身很容易变成新的关键路径。正确做法见
  [`../storage-flow/skid-buffer.md`](../storage-flow/skid-buffer.md)
  和 [`backpressure-paradigms.md`](backpressure-paradigms.md)。
- **数据寄存器通常不要复位，控制寄存器必须复位。** 给 32 位数据流水寄存器
  加异步复位是白付面积和复位树扇出；`valid` 不复位则是致命 bug。
  见 [`../storage-flow/reset-strategy.md`](../storage-flow/reset-strategy.md)。
- **不要用 `PIPE_STAGES` 参数同时改变功能。** 常见错误是流水版本顺手改了
  舍入/饱和行为，于是 PPA 对比里混进了功能差异。参数扫描的前提是
  **所有档位功能等价**（延迟可以不同）。
- **保层级（`params.yaml` 的 `keep_hierarchy:`）在这里通常不必要**：不同 `PIPE_STAGES` 的触发器数
  不同，工具不会把它们收敛成一个。**但只要同一次实验里还在比微架构
  （比如 `CARRY_STRUCT`），就仍然要加** —— 本仓库的 adder32 正是这种情况
  （`docs/pitfalls.md` 的 P-3）。

## 参数化接口建议

> 接口按本仓 RTL 命名约定写（`rtl-structure-authority`，2026-09-28）：参数 `DAT_W` / `*_W` / `*_N` / `*_EN` / `SCHEME`，端口 `i_` / `o_` 前缀，握手 `i_vld/o_rdy/o_vld/i_rdy`。

```verilog
module DUT #(
    parameter DAT_W       = 32,
    parameter PIPE_STAGES = 1,     // 0 = 纯组合
    parameter BALANCED_EN = 0      // 切点策略：0 EVEN（等分位段） | 1 BALANCED（按实测延时切）；二选一写成 _EN（D16）
)(
    input clk, rst_n,
    input                  i_vld,
    input  [DAT_W-1:0]     i_a, i_b,
    output                 o_vld,
    output [DAT_W-1:0]     o_dat
);
```

`BALANCED_EN`（切点策略）是这张卡真正想测的东西：**同样的级数，切点不同 fmax 差多少。**
`EVEN` 按位段等分（写起来简单，但进位链上各段延时并不相等），
`BALANCED` 按上一轮实测的延时分布调整切点。这个对比能直接量化"级平衡"值多少钱。

## 本地实测

**本知识库第一张挂上实测记录的卡。** 本仓库 `designs/adder32`（该设计根 2026-10-02 删除、2026-10-14 恢复为演示设计，RTL 改写前后形式等价；历史记录的源码仍按记录的 `git_commit` 取，见 `docs/data-credibility.md` 的 D-29），
三种进位结构 × `PIPE_STAGES = 0/1/2` 共 9 个组合都有记录，
代表记录（`CARRY_STRUCT = CLA`）：`adder32-CLA-0-d64230f4` /
`adder32-CLA-1-42d872bd` / `adder32-CLA-2-5990de82`；
另外两种结构的记录同批，按 `params` 在实验记录（`results/<设计根>/experiments.jsonl`）里检索。

三个结论，第一个推翻了这张卡初稿里的说法：

1. **流水加速比的上限由"该结构的延时如何随位宽增长"决定，不是由级数决定。**
   本仓库把 `WIDTH` 扫成 8/16/32/64 之后，这条可以直接量出来了 ——
   延时对位宽的 log-log 斜率：**RIPPLE 1.012**（O(n)，面积斜率也恰好 1.000）、
   **CSEL 0.573**（O(√n)，面积斜率 1.002）。两者都和理论值吻合得很好。

   于是"理想加速比"有了正确的算法：**不是 N 倍，而是同一结构在半宽下的实测延时比**。
   按这个基准，切 2 段的效率是：

   | 结构 | 理想（32 位延时 / 16 位延时） | 实测加速 | 效率 |
   |---|---|---|---|
   | RIPPLE | 2.014× | 1.948× | **96.7%** |
   | CLA | 1.697× | 1.574× | **92.8%** |
   | CSEL | 1.680× | 1.492× | **88.8%** |

   **三者都在 89~97%，剩下那几个百分点就是每级的 `t_setup + t_cq`。**
   这才是"级平衡效率"该有的样子；用线性理想（N 倍）去套，会把
   O(√n) 结构的效率错算成 70% 出头，然后归咎于根本不存在的切点问题。

   **推论：结构越快（斜率越小），流水化能买到的加速上限越低。**
   给已经很快的电路加流水，付的面积一分不少，拿回来的频率却少得多 ——
   CSEL 的理想上限只有 1.68×，而 RIPPLE 有 2.01×。
2. **但每单位加速的面积代价三种结构相当一致**：
   `(面积增幅) / (加速倍数增幅)` 落在 **0.45~0.63** 之间，六个数据点没有例外。
   也就是说"加速 1 倍大约要多付 0.5~0.6 倍面积"是个跨结构稳定的兑换率，
   **结构的选择改变的是你能买到多少加速，不是单价。**
3. **逻辑级数收敛得比延时快**（CLA 22 → 16 → 14），说明第二刀已经开始碰到
   "切不动"的段（进位链里有一段无法再分）。第三刀大概率不划算。

⚠️ **CLA 那一行的斜率不可用于渐进阶论断。** 本仓库 `adder32` 的 `CLA` 分支
（`rtl/flat_lookahead.v`）是完全平铺的与或式而非真前缀网络，深度靠综合启发式重构，
实测面积斜率 1.239、延时随位宽非单调（64 位比 32 位快）。
上表里 CLA 的 92.8% 仍是有效测量（它是那个具体电路在 32/16 位上的真实比值），
但**不要把它当成"O(log n) 结构"的代表**。详见 `docs/data-credibility.md` 的 C-1。
真正的前缀网络见 [`../arith/prefix-adders.md`](../arith/prefix-adders.md)。

⚠️ 三条使用限制（契约在 `openspec/specs/experiment-record/spec.md` 的
「记录必须携带可比的性能标量」，读数口径在 `docs/data-credibility.md`）：
`fmax` 是 `analytic`（`1000 / 关键路径延时`）、**setup-only、单角 TT、
无时钟不确定度和 OCV 的理想值**，横向比架构有效，**不要当成"真能跑到 3.2 GHz"往外报**；
它还是**未加时序压力**的值 —— 综合时没有给延时目标，所以这是"关键路径恰好有多长"，
不是"这个架构能跑多快"（`docs/data-credibility.md` 的 D-7，
修法见 内部#26）；
功耗一列因为反标失效不可用（`docs/data-credibility.md` D-1），所以上表没有功耗。

**还没测的**：`CUT_POLICY`（切点策略）。这是这张卡最该补的一个实验，
而且它不依赖任何流程改造 —— 纯 RTL 参数。
