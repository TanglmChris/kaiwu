# <设计> 阶段整理 · <起止版本>（模板）

> G10（内部#213，用户 2026-10-05）：每个大版本发布后做一次阶段整理。项目经理开一个 issue，正文用本模板；
> 各会话一个会话一条评论交清单；项目经理出阶段总结（存进设计根 `doc/phase-<起止版本>.md`）与三张表。
> **删除和推送一律先列清单**，由用户批准；关 issue 由项目经理汇总成一张表，用户一次批准。不占关键路径，空闲时做。

## 各会话交的清单（一个会话一条评论）

1. **做完了什么**：本阶段的产出与关键数字（附命令或记录出处）；
2. **定了什么**：用户拍板过、与本会话相关的决定（issue 链接）；
3. **教训**：踩过的坑，是否已写进能长期生效的地方（pitfalls / toolchain / skill / memory），没写的列出来；
4. **flow 可优化项**：手工做、反复做、容易错的流程环节（flow 汇总后开 issue）；
5. **keel 可优化项**：各会话直接开 keel issue（先问用户），这里列链接；
6. **文档**：本会话负责的文档有哪些过时、重复、互相矛盾；
7. **可以关的 issue**：编号 + 一句结论 + 证据链接；
8. **worktree / 分支 / runs / scratchpad**：本会话建过的，列路径或分支、用途、是否已合入、能不能删（**只列，不删**）；
9. **带进下一阶段的事项**；
10. **应该写成规范的做法**：写明建议放进 toolchain / spec-writing / 模板 / skill 的哪一节（flow 汇总后定）。

## 分工

| 范围 | 谁 |
|---|---|
| memory（全仓共用一个目录） | 项目经理在各会话交清单之后统一整理；其他会话只改自己的条目（`<角色>-<主题>.md`） |
| 项目路径本身（仓库布局、残留目录、未跟踪文件、重复内容） | flow 盘点并提方案 |
| flow 可优化项 | 各会话列，flow 汇总分拣开 issue |
| 规范候选（第 10 项） | flow 定哪些进规范、放哪一节；改之前 grep 原文 |
| 文档 | 设计文档归规格；全仓文档（toolchain、CLAUDE.md、pitfalls、data-credibility）归 flow |
| worktree 和分支 | 项目经理只读盘点出总表，用户批准后由属主会话删 |
| issue 关闭 | 项目经理汇总成表，用户一次批准 |
| 阶段总结 | 项目经理写，从项目计划 issue 与主线 issue 链过来 |
| 换班 | 交完清单后按 toolchain「换班」一节，`keel shift` |

**时间**：各会话 <日期> 内交清单；项目经理 <日期> 出总结和三张表（issue、worktree / 分支、memory 改动）。
